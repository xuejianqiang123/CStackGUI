# 文档 ↔ 代码事实同步

**同步范围**：$ARGUMENTS

> 来源：2026-10-17 从上游 ai-dev-kit（`D:\CPro\.codebuddy`）同步并适配到本工程
> （Win32/GDI+ 桌面工具包 + 画布；权威分布与门禁名已换成本工程口径）。

文档腐化比代码腐化更隐蔽：**它不阻止编译、不触发任何门禁、只伤害读它的人**。
对本工程这种"AI 读文档干活"的工程，腐化的代价被直接放大：读到"未实现"就会重复造一遍、
把已经修好的问题重新上报。而这些错误**看起来都像是照文档办事**。

## 核心原则

1. **代码是事实源，文档是缓存。** 任何"X 是否已实现"的结论，最终以**代码实测 + 机械判据**为准；
   文档与代码冲突时，**改文档**（除非代码本身确实错了，那是另一个需要独立证据的判定）。
2. **一个事实只能有一处权威。** 状态记在多处时，必有互相矛盾的副本。
3. **按维度分权威，不要混。** 最常见的自伤是"结构类权威"与"状态类权威"打架：
   `.cgui` 字段语义、控件类型表该由代码说话，技能清单/计数该由索引+门禁说话——
   用一份去答另一类问题，就会出现无解冲突。
4. **只登记能被别人复核的事实。** 登记"某功能已完成"必须带**可复核的落点**（文件:行号 / 门禁输出 / 单测结果）；
   写不出落点的，等于没登记。

## 腐化信号自查（每项都能机械检查，不靠感觉）

| # | 信号 | 检查方法 | 后果 |
|---|---|---|---|
| 1 | 状态词与代码事实矛盾 | 文档里的"未实现 / 缺 / TODO" → 逐条按 `evidence-discipline` 三段取证核实 | AI 跳过已实现功能 / 重复实现 |
| 2 | 新增组件没回写文档 | 目录实测组件列表 与 文档组件清单求差，看是否为空；本工程同族：控件类型 / 事件 / 动作 / 支持库四处跨端表 | AI 认为模块不存在 → 重复造轮子 |
| 3 | 同一状态被记在 ≥3 处 | 关键词全仓搜（未实现 / 已完成 / Out of Scope / 缺失）看落点分布 | 任一处过期即产生矛盾，且没人知道该信谁 |
| 4 | 仲裁规则自身打架 | 搜两处以上"现状以…为准"，看是否指向不同对象 | 冲突时无解，AI 各挑一个 |
| 5 | 数字腐化 | 用例数 / 门禁道数 / 文件数 / 技能数 / 支持库条数写死在文档里。**根治做法是改引用形态**：技能总数由 `node tools\check-skills.mjs` 机器校验；支持库条数以编译后的 `cstackgui.h` 为准。手写的第二份就必然腐化 | 读者按不存在的数字找东西 |
| 6 | 章节编号与物理顺序脱节 | 编号是跨文档引用的稳定标识；乱序会让检索落空 | `§5.2` 被检索到 `§8` 段落里 |
| 7 | 反向引用无门禁 | 文档里"依据 PRD §X"这类纯文本引用，没进任何链接检查 | 目标章节被删或改名后**静默失效** |
| 8 | 例外表/基线吞掉了真实问题 | 基线数只增不减 ⇒ 门禁从"报红"退化成"不新增红" | 债务隐形，且被误读为"已清理" |

## 同步的两个方向（只做一个方向 = 半个失效）

**向前（新增事实 → 回写登记）**：新增/删除/改名组件或功能时，把"该登记哪几处"一次性列全并逐项打勾。
本工程的清单在 `designer-modify`（画布侧改动要动的 7~8 处）与各技能的产出物规范里，本技能不重复，只补一条纪律：
**登记点要与"权威归属"对齐——状态只登记到权威那处，其它地方放指针，不放副本。**

**向后（存量事实 → 校验与回写）**：本技能的重点。默认动作顺序：

1. **先确认权威是谁**（这一步不能跳）——某份文档/某张表/某个生成物被明确指定了吗？
   指定了多处且互不相同 ⇒ 先解决"权威冲突"，再谈同步（否则你在往错误的权威里写正确内容）。
2. **代码实测**：文件存在？已登记？已接线？（`evidence-discipline` 三段取证）
3. **机械判据**：相关门禁/单测结论。**先确认判据的扫描域包含目标**，再看红绿。
4. **机器生成物优先**：能用脚本生成的清单/计数，**不要手写进文档**。
5. **回写落后的那一方**，并在同一处标注"以 X 为准"，让后来者不必重新裁决。
6. **能加门禁就加门禁**：凡是"人工核对就能发现"的腐化，都应该变成机械判据
   （否则下一次仍要靠人记，且人一定会忘）。新增门禁必须满足：**能自证会判红**（正反例各跑一次）。

## 冲突裁决顺序（可执行，不靠和稀泥）

```
代码实测（存在 → 登记 → 接线）
  ↓ 若代码证据不足
机械判据输出（且已确认其扫描域覆盖目标）
  ↓ 若仍不足
机器生成物 / 单一权威声明
  ↓ 若仍冲突
按维度分权：状态类听生成物，结构类听代码与分层规范；两边都不是 → 记为"待裁决"，不擅自选边
```

**禁止的裁决方式**：

- ❌ 多数投票（文档里 3 处这么说 vs 2 处那么说，不构成证据）
- ❌ 取最新修改时间（新文档也可能是错的）
- ❌ 采信引用链上游（转述不是证据）
- ❌ 折中（"两个都写上，加括号说明" = 把矛盾扩散给所有读者）

## 与其它技能的关系

- `evidence-discipline`：提供**取证动作**；本技能提供**同步与裁决流程**。先取证，再同步。
- `designer-modify`：画布侧改动的**向前**登记清单。
- `piv-implement` / `git-commit-style`：收口阶段调用本技能做"事实 → 文档"的一致性收口（提交前的文档同步环节；文档跟着代码走，不单独提交）。

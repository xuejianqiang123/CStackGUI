# 验证改动

**验证聚焦（可选）**：$ARGUMENTS

验证改动是否真正可用，而不是"看起来能编译"。

## 验证层级（从低到高，逐级通过）

### 第 1 级：编译与静态检查（必做）
```bash
# 1. 工作区卫生
git diff --check          # 空白错误、冲突标记
git status                # 确认改动范围

# 2. 编译（ESP-IDF 项目，在对应子项目目录）
idf.py build              # 或项目指定的构建脚本（system_release.sh 等）

# 3. 新增警告检查
#    编译输出应无新增 warning/error；对比改动前后警告数
```

### 第 2 级：静态分析与单测（尽量做）
```bash
# 单元测试（tests/ 目录，若项目有对应测试）
# 查看 tests/ 下的构建方式，运行与本改动相关的测试

# 代码审查（可选，项目已有工具）
python ai_code_review.py  # 按项目 CI 方式触发，或按 docs 说明
```

### 第 3 级：行为验证（必做，核心）
按实现计划中的验证方法逐条执行：

- **逻辑类**（协议解析、校验、状态机）：用单测或 host 端模拟验证
- **驱动类**：真机回环测试（如 UART 自发自收）、示波器/逻辑分析仪确认波形
- **集成类**：真机联调，验证数据链路完整

> 涉及 UART/串口协议/日志输出的改动，用 `serial_verify` skill 做串口实测（烧录→观察真实输出→回环/应答→异常注入），把验证从"编译过"推进到"设备实测过"。
- **边界与异常**（嵌入式必查）：
  - 超时路径（接收超时、命令超时）
  - 错误帧/坏校验
  - 缓冲区满/数据长度越界
  - 重入/中断打断
  - 上电时序/掉电

## 验证通过标准

以下全部满足才算验证通过：

- [ ] `git diff --check` 无输出
- [ ] 编译无新增错误和警告
- [ ] 所有计划中的验证方法已执行且通过
- [ ] 边界/异常路径已覆盖（或明确记录为已知风险）
- [ ] 涉及变更的文件，相关单测通过

## 验证失败时的处理

1. 定位：读取失败相关代码，理解原因（不要盲目修改）
2. 修复：小步修改，重新编译
3. 重验：重复直到通过
4. 如果验证方法本身有问题：更新计划中的验证方法，说明原因

## 输出

报告验证结果清单（每项：通过/失败/跳过+原因），失败的项必须附修复说明。

全部通过后才允许进入 `piv-review-changes`。

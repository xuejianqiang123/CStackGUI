# 需求澄清与 PRD 编写

**需求描述**：$ARGUMENTS

将模糊需求转化为一份结构化、可评审、可执行的 PRD。

## 核心原则

- **对终点具体，对手段放权**：目标、验收标准必须精确；实现路径不做过度约束。
- **Tight Scope 优先**：宁可小范围彻底交付，不要大范围半成品。
- **Explicit Non-Goals**：明确列出"本期不做"，防止范围蔓延。
- **指标可测量**：验收标准必须是可验证的（能测、能看、能量）。

## 澄清问题清单（先问再写）

开始前先向用户确认以下信息（按需，不机械全问）：

1. **业务目标**：这个功能解决什么问题？给谁用？（最终用户/产线/调试）
2. **边界**：影响哪些模块、哪一层（`runtime/src` 四层 / 画布 / `cg_kit`）？会不会动到 `.cgui` 字段或控件类型表（那要三处同步）？
3. **硬件约束**：涉及哪些外设（UART/SPI/I2C/DMA/GPIO/Flash）？引脚或通道是否已占用？
4. **通信协议**：如果涉及通信，协议帧格式、波特率、超时、校验是否有约定？
5. **验收标准**：怎样算完成？（产线测试项/上位机行为/指示灯状态）
6. **非目标**：明确不做哪些？
7. **兼容性**：是否需要兼容旧版本协议/配置（如 NVS 存储结构变更）？

## 输出格式

将 PRD 保存到 `docs/PRD_<feature_name>.md`（项目已有 PRD 文档，风格保持一致）：

```markdown
# PRD：<功能名称>

## 1. 背景与目标
- 问题描述
- 目标（可测量）
- 非目标（Explicit Non-Goals）

## 2. 需求详情
### 2.1 功能需求
- 用户故事：作为<角色>，我希望<动作>，以便<价值>
### 2.2 硬件/外设需求
- 引脚、外设、时钟、功耗约束
### 2.3 通信协议需求（如有）
- 帧格式、波特率、超时、校验、错误处理

## 3. 验收标准（Acceptance Criteria）
- 每条必须可验证：Given/When/Then 格式

## 4. 依赖与风险
- 依赖的组件、硬件版本、工具链
- 风险与缓解

## 5. 范围管理
- In Scope / Out of Scope 清单
```

## 检查清单（输出前自查）

- [ ] 验收标准全部可测量、可验证？
- [ ] 非目标已明确列出？
- [ ] 硬件/协议约束已澄清？
- [ ] 文件已保存到 `docs/` 并命名规范？

## 完成后

- 告知用户 PRD 路径，请其确认验收标准是否准确
- 确认后，建议下一步运行 `plan-architecture` 或 `piv-slice-epic`

# 技能：串口行为验证（Serial Behavior Verification）

**验证目标（可选）**：$ARGUMENTS

## ⚠️ 核心原则（第一性原理：验证的本质是"证明它在设备上真的工作"）

- **编译过 ≠ 工作**：`idf.py build` 只证明语法和链接正确，证明不了运行行为。嵌入式的真正验证必须落到设备上。
- **观察真实输出**：以串口日志 / RTT 输出为"事实源"，而不是靠推断代码逻辑得出"应该没问题"。
- **先定判据再动手**：动手前先写清"看到什么算通过、看到什么算失败"，否则串口输出只是一堆无意义的字符。
- **异常路径必测**：正常路径能过是最低要求；超时、坏帧、断连、缓冲区满这些异常路径才是嵌入式 bug 高发区。

## 触发条件

- `piv-validate` 进入第 3 级行为验证，且改动可在真机 / host 端观测
- 改动涉及 UART / 串口协议解析 / 命令行 / 日志输出
- 需要确认固件"烧进去后到底跑成什么样"
- 用户明确要求：烧录、串口监控、回环测试、命令应答实测、异常注入

## 🔍 验证操作清单

### 第 1 步：确定验证判据（动手前必做）

在打开串口之前，先写清楚每条要验证的行为对应的**期望输出**：

| 验证项 | 触发动作 | 期望看到 | 判为失败 |
|--------|---------|---------|---------|
| 启动正常 | 上电 / 复位 | 启动 banner + 版本号 + `init ok` 类日志 | panic、`Guru Meditation`、看门狗复位循环 |
| 命令应答 | 发送命令帧 | 对应 ACK / 回显 / 状态变化 | 无响应、错误码、超时 |
| 回环 | 自发自收 | 收到 == 发出 | 丢字节、错位、乱码 |

> 没有明确判据的串口观察不算验证，只算"看热闹"。

### 第 2 步：连接与烧录

```bash
# ESP-IDF：烧录 + 监控一步到位（在对应子项目目录）
idf.py -p <PORT> flash monitor

# 只监控（固件已在板上）
idf.py -p <PORT> monitor

# 通用串口监控（非 IDF 环境 / 快速看输出）
# Windows(Git Bash) 下 PORT 形如 COM5；Linux 形如 /dev/ttyUSB0
```

**波特率**：ESP32 默认日志 115200；自定义协议按项目实际配置。波特率不对 → 全是乱码，先排除这一项再怀疑代码。

> ⚠️ 烧录会覆盖设备现有固件、影响真实硬件，属于中风险操作。执行前确认端口对应的是目标板，不是其它在用设备。

### 第 3 步：正常路径实测

- 观察启动日志：是否走到 `app_main` / 主任务、外设初始化是否 `ok`
- 触发核心功能，比对**实际输出**与第 1 步的**期望输出**
- 关键：把实际串口输出**贴进验证记录**，不要只写"正常"

### 第 4 步：回环 / 命令应答实测（按改动类型选）

```
UART 回环：TX 接 RX（或软件回环），发送已知序列 → 校验收到的完全一致
命令应答：逐条发送命令帧 → 记录每条的响应 → 比对协议定义
```

比对要点：字节数一致、内容一致、时序在超时窗口内。

### 第 5 步：异常路径注入（嵌入式必做，最容易暴露 bug）

按改动实际涉及的路径注入异常，逐条记录设备表现：

| 异常类型 | 注入方法 | 设备应有的正确表现 |
|---------|---------|------------------|
| 接收超时 | 发不完整帧后停止 | 超时后返回错误码 / 丢弃半包，**不卡死、不复位** |
| 坏校验 | 发 CRC 错误的帧 | 拒绝该帧并记日志，**不误动作** |
| 缓冲区满 | 高速灌超长数据 | 丢弃或分片，**不溢出、不 panic** |
| 断连重连 | 拔插 / 断电重启对端 | 能恢复通信（对应重连策略） |

**判据**：设备在异常下要"优雅降级"，而不是崩溃 / 卡死 / 无限复位。任一条导致 panic 或死等，即为验证失败。

---

## 强制规范

1. **判据先行**：无期望输出，不开始串口验证。
2. **贴事实**：验证记录必须包含**真实串口输出片段**（正常 + 异常各至少一段），禁止只写结论。
3. **异常必覆盖**：涉及协议 / 收发的改动，第 5 步异常注入至少覆盖"超时"和"坏帧"两项。
4. **失败追根因**：串口暴露的问题，回到代码定位根因（配合 `communication_protocol_check`），不在验证脚本层打补丁掩盖。
5. **端口安全**：烧录前确认目标端口，避免误刷其它设备。

## 与 PIV 工作流的关系

本 skill 是 `piv-validate` **第 3 级行为验证**的执行手段，专门补齐"编译过 → 设备实测过"这一环：

```
piv-validate
├─ 第 1 级 编译 + 静态检查（idf.py build / git diff --check）
├─ 第 2 级 静态分析 + 单测
└─ 第 3 级 行为验证 ──→ 【serial_verify】串口实测（本 skill）
                         正常路径 + 回环/应答 + 异常注入
```

- 逻辑类改动（纯解析 / 校验）可用 host 端模拟，不一定需要真机；驱动 / 通信类改动**建议真机跑本 skill**。
- 验证失败 → 回到 `piv-implement` 修复，配合 `communication_protocol_check` 定位协议层根因。

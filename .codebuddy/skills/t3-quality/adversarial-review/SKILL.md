# 对抗式代码评审（三角色互相审判）

**输入**：$ARGUMENTS

> 来源：2026-10-17 从上游 ai-dev-kit（`D:\CPro\.codebuddy`）同步并适配到本工程
> （Win32/GDI+ 桌面工具包 + 画布；固件专属内容已替换为本工程判据）。

把"AI 自己检查自己"换成 **指控 → 复核 → 修复** 三方分离，且**指控必须带证据、复核必须先找反证**。

## 为什么需要它（AI 自查的两种失效）

| 失效 | 表现 | 后果 |
|---|---|---|
| **自我辩护**（最常见） | 刚写完的代码再看，倾向于证明自己对 ⇒ 输出"审查通过，未发现问题" | 真 bug 静默溜过 |
| **自我指控过头** | 为显得彻底，把"可能"当"必然"、把 60 处同类当 60 个 bug | 修了一堆**不存在**的问题，改坏好代码 |

单角色同时躲不开这两种失效；三角色把它们分给不同角色，**各自只负一种责、且互相否决**。

## 与 `adversarial-thinking` 的分工（不要重复造）

| | `adversarial-thinking` | `adversarial-review`（本技能） |
|---|---|---|
| 层 | 决策层（给建议**前**攻击自己的结论） | 评审层（审查门禁的**执行协议**） |
| 对象 | 自己的**结论/建议/整改清单** | **代码改动** |
| 产出 | 确定项 / 已否掉项 / 降级项 | 三方裁定表 + 修复清单 + 回归判据 |
| 关系 | 挑刺者与辩护者的**武器库** | 在 R2/R3 中调用它 |

> 与 **P3 攻击自测**（`piv-validate` / `piv-run-full-loop`）的分工：那是**实现者**在写码时打自己的实现；
> 本技能是**评审者**在审查门禁审判已完成的改动。视角不同，**两个都要做**；
> 但 R2 不重复列"已被验证判据覆盖且通过"的攻击面（引用即可，避免同一问题走两遍流程）。

## 核心原则（4 条）

1. **无证据不指控**：每条问题必须带 E1 以上证据（见下表），E0 直接丢弃、不进报告。
2. **辩护者先找反证**：辩护者默认立场是"**挑刺者是错的**"，逐条尝试否掉；反证找尽才判成立。**全盘成立 = 辩护者失职。**
3. **改进者只修裁定成立的**：驳回项**不许动手**；跨语义决策（产品 / 协议 / 观感该是什么值）一律降级为观测。
4. **修好要能被证伪**：每条裁定成立的 critical/high，必须配一条**能变红**的回归判据（单测 / 门禁 / 真机命令）。

## 证据分级（指控的准入门槛）

| 级 | 含义 | 例子 | 处置 |
|---|---|---|---|
| **E0** | 断言，无依据 | "这里可能有竞态" | **丢弃**，不进报告 |
| **E1** | 代码引用（文件+行+片段） | `runtime/src/skin/cg_skin_edit.c:128` 重画时没先填边框带 | 可提，标"未验证可执行性" |
| **E2** | 可执行判据（命令/单测/门禁能复现） | 加一例单测后变红；`tools\check-format.bat` 红 | 强证据 |
| **E3** | 真机实测 / 变异自检 | 真窗口键鼠探针复现；改坏→红→恢复绿 | 最强 |

> 严重级（critical/high/medium/low）只由**后果**定，不由证据等级定；但 **critical/high 必须有 E1 以上，且尽力做到 E2**。

## 流程（R1~R5）

### R1 定范围与收集（沿用 `piv-review-changes` 第一/二步）

- `git --no-pager status --short` / `git diff HEAD` / `git ls-files --others --exclude-standard`
- **范围从 `git status` 枚举，不手写**（手写清单必漏；未跟踪新文件也要进候选池）
- 按领域加载 7 个审查技能（映射见 `global-rule.md` §7 / `sop` §4）收集候选 ⇒ 得到**候选池**（此时不判成立）

### R2 挑刺者（Critic）：带证据指控

对候选池每条产出一行：

```
C-01 | 文件:行 | 类别 | 严重级(自评) | 证据(E1/E2/E3) | 触发路径(必须真实存在) | 后果
```

硬约束：

- [ ] 每条都跑一遍 `adversarial-thinking` 阶段一「攻击事实」清单：调用点是否只有这一处 / 别的层是否已做 / 开关当前是开还是关 / 例外表与白名单的键是否失配 / 初值本身是不是坏值 / 是不是环境假象（exe 被残留进程锁住 / 窗口没真在前台 / GBK 管道）
- [ ] **只指控，不给修复方案**（给方案会污染辩护者的独立判断）
- [ ] 禁止"可能有""建议关注"这类 E0；写不出触发路径的，要么读到能写出来，要么丢弃
- [ ] 只审本次改动集，不顺手扩范围
- [ ] **必加载对口审查技能并逐文件（不是抽样）覆盖"注释/文档规范"面**：引 `firmware_code_style` 核对**每个公共函数是否有函数头注释**（`@brief/@param/@return`）、注释形态。上游仓 2026-10-07 实测漏项：代码缺陷面（内存/错误码）全绿，注释面却整体失守——因为 R2 只盯着代码缺陷。这类"规范类"失守不产生运行期 bug、但会被用户一眼看穿，**必须与代码缺陷同列攻击面**。本工程对应判据：`tools\run-tests.bat` 的 check-comments 门禁。

### R3 辩护者（Defender）：独立复核裁定

**默认立场：挑刺者是错的。** 对每条 C-xx 逐条找反证：

- [ ] **重读原文**，不采信挑刺者的转述与代码片段
- [ ] 找**保护性代码**：调用方/上层是否已校验、是否有断言、是否有默认值兜底
- [ ] 查**开关与构建**：这段代码当前编译进去了吗（`#if XXX_EN`）？该分支跑得到吗（前置条件 / 窗口是否存在 / `cg_app_has_window()`）？
- [ ] 查**同类已修**：是不是已被别处同一机制覆盖（教训：只 grep 一个模块就断言"从不 X"，别的层可能已做）
- [ ] 算**真实后果**：触发概率 × 危害。偶发且无害 ⇒ 降级；不是所有"不严谨"都是 bug

裁定三态（逐条写理由）：

| 裁定 | 含义 | 后续 |
|---|---|---|
| **成立** | 反证找尽，缺陷真实且后果成立 | 进 R4；critical/high **必配回归判据** |
| **降级** | 缺陷真实但后果小于指控（频度/危害/开关关着） | 改严重级后进 R4，或转为"观测" |
| **驳回** | 反证成立（已有保护 / 路径到不了 / 语义本就如此） | **不改代码**，写清"为何不是 bug"，防后人误改 |

健康度自检（写进报告，是判据不是装饰）：

- 成立率 **100%**（⇒ 驳回率必然为 0%）⇒ 辩护者是橡皮图章，**重做 R3**
- 驳回率 **≥ 80%** 且条目 **≥ 6** 条 ⇒ 挑刺者在凑数，**重做 R2**（驳回须附反证出处，"无出处的驳回无效"）
- 驳回项**必须附反证出处**（文件:行 / 开关值 / 命令输出）；**无出处的驳回无效**

### R4 改进者（Fixer）：只修裁定成立的

对每条"成立 / 降级"：

- [ ] 最小改动（`ponytail`）：改根因，不顺手扩范围
- [ ] 同类全覆盖：同缺陷的三个宏 / 三处调用一起修（只修被调用的那个会留坑）
- [ ] 跨语义决策 ⇒ **只加观测、不改行为**，写清根治方向与本轮不做的理由
- [ ] 配回归判据（三选一，且先自问"**它有问题时会红吗**"）：
      `tools\run-tests.bat` 新用例（含**变异自检**：改坏→红→恢复绿）/ `tools\check-format.bat` 门禁 / `serial_verify` 真机命令
- [ ] 改完**重跑验证**（`piv-validate` 对应级别），不是"改完就算修"

> 改进者的**修复方案本身**再过一次 `adversarial-thinking`：修这个会不会引入新问题。

### R5 落报告

并入 `piv-review-changes` 的报告 `.codebuddy/code-reviews/<date>-<feature>.md`：

```markdown
## 对抗式评审（三角色）
候选 N 条 → 指控 M 条 → 裁定：成立 X / 降级 Y / 驳回 Z
健康度：成立率 x% ｜ 驳回率 z%

| ID | 位置 | 指控 | 证据 | 裁定 | 反证/理由 | 处置 | 回归判据 |
|---|---|---|---|---|---|---|---|
| C-01 | cg_skin_edit.c:128 | ... | E1 | 驳回 | cg_win_draw.c:88 已先填底色 | 不改 | — |
| C-02 | cg_serial.c:31 | ... | E2 | 成立 | — | 加边界判 | run-tests 新例（变异：去掉判据→红） |

### 驳回项（防后人误改）
- C-01：<为什么不是 bug，附反证出处>
```

## 独立性保障（最关键，也最容易流于形式）

同一模型串行演三角色会互相污染。二选一：

- **A 协议隔离（默认，零成本）**：R2 只写指控不写方案；R3 **重读原文**、不采信 R2 转述；R4 只看裁定表。**三段分三次输出。**
- **B 真并行（critical 有争议 / 大改动）**：用 `team-parallel-delivery` 把三角色派给三个子代理，**各自独立读码**，汇聚后由主代理汇总裁定。

**禁止**：在一次输出里同时给出"问题 + 裁定 + 修复"——那是自证自话，等于没做对抗。

## 反模式

- ❌ 挑刺者直接给修复方案（污染 R3）
- ❌ 辩护者复述挑刺者的代码片段当复核（这不是独立）
- ❌ 全盘成立（和稀泥）；或用数量代替后果（60 处 ≠ 60 个 bug）
- ❌ 修了"驳回"项
- ❌ 裁定成立却没配**能变红**的回归判据
- ❌ 把"未验证"写成"已修复"

## 输出

三方裁定表 + 驳回项说明 + 修复清单（含回归判据），并入 `.codebuddy/code-reviews/<date>-<feature>.md`。

## 配套

`piv-review-changes`（宿主门禁）｜ `adversarial-thinking`（武器库）｜ `serial_verify`（真机判据）｜ `ponytail`（最小修复）｜ `team-parallel-delivery`（真并行派发）

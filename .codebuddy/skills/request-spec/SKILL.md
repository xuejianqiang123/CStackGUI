# 请求规格化

**原始请求**：$ARGUMENTS

> 来源：2026-10-17 从上游 ai-dev-kit（`D:\CPro\.codebuddy`）同步并适配到本工程
> （Win32/GDI+ 桌面工具包 + 画布；素材/约束/交付三元已换成本工程口径）。

本工程里 AI 输出差，**最常见的原因不是能力不够，而是请求本身缺元**：
缺素材依托 ⇒ 必然虚构；缺约束 ⇒ 越界改动；缺交付场景 ⇒ 详略全错。

本技能只补这一环：**动手前把请求补全成规格**，然后交回领域技能执行。

## 核心原则

1. **约束密度决定输出质量**，而不是请求的长度或语气。
2. **可推断的就别问**——先声明假设并继续；只问"**猜错会导致返工**"的阻塞项，且**一次不超过 3 个**。
   （同 `ponytail`：能不写就不写；这里对应"能不问就不问"。）
3. **本技能不做执行**：规格成型后按「转交表」交给对应领域技能，不复制它们的规则。

## 七元规格（唯一必背）

| 元素 | 回答什么 | 缺失的后果（本工程实例） |
|---|---|---|
| **明确角色** | 你让 AI 当谁？ | 输出平均化、无专业度 |
| **精准任务** | 动词 + 对象 + 边界 | "帮我看看" ⇒ 不知道看什么，只能泛泛而谈 |
| **素材依托** | 依据什么**真实材料**？ | **没素材 ⇒ 必然虚构**（最致命，同 `evidence-discipline`） |
| **固定结构** | 分几段、每段叫什么？ | 顺序混乱、漏项 |
| **格式要求** | 表格 / 清单 / 是否给命令？ | 不能直接拿去用 |
| **约束条件** | 不能做什么？ | 顺手重构、越层 include、新增门禁例外 |
| **交付场景** | 给谁看、用在哪？ | 语气与详略全错 |

## 本工程场景的三条特化映射

通用提示词在本工程失效，就是这三元没补齐：

| 七元 | 本工程的等价物 |
|---|---|
| **素材依托** | **仓库路径 + 具体文件 +（编译输出 / 单测日志 / 截图 / 串口输出）**。三样缺一，结论就只能靠猜 |
| **约束条件** | **分层**（`runtime/src` 的 core / win32 / skin / kit，业务代码只 include `cstackgui.h`）+ **范围**（只改必需文件、不顺手重构、不新增门禁例外）+ **红线**（`safe-file-ops` 不删手写文件、`ponytail` 红线不砍） |
| **交付场景** | **可执行判据**：`build-all.bat` / `tools\run-tests.bat` / `tools\check-format.bat` / `cd designer && npx tsc --noEmit && npx vite build` / `serial_verify` 里能真正跑起来并**能变红**的命令 |

## 流程（逐条打勾）

### 步骤 1：判定缺失元

- [ ] 给足了**路径 + 文件**吗？（只有模块名 ⇒ 缺素材）
- [ ] 有**动词**吗？（"看看 / 弄一下" ⇒ 缺任务）
- [ ] 有**产出形态**吗？（表格 / 清单 / 直接改代码 / 只报告）
- [ ] 有**边界**吗？（改哪些、不改哪些）
- [ ] 有**判据**吗？（怎么算做对了）
- [ ] 涉及**事实结论**吗？（"有没有做 / 谁对" ⇒ 同触发 `evidence-discipline`）

### 步骤 2：缺失项分类，别一股脑问

| 分类 | 判据 | 处置 |
|---|---|---|
| **可推断** | 本工程有明确惯例（如默认只 include `cstackgui.h`、默认跑 `build-all.bat`） | **声明假设并继续**，在输出开头写明"我假设 X" |
| **可默认** | 有本工程默认值（如默认只报告不改码、报告落 `.codebuddy/code-reviews/`） | 按默认值执行，末尾注明 |
| **必须问** | **猜错会导致返工**（改错文件、判错"是否已实现"、动错跨端契约） | 才问，且 ≤3 个，尽量给选项 |

> 反例（禁止）：把七元全部列成问题丢回给用户——那是用"提问"替代"思考"。

### 步骤 3：回填规格并复述

用一段话把七元写全，**开工前先复述一遍**让用户能一眼纠偏：

```text
我按这个规格执行：角色=【】；任务=【动词+对象+边界】；素材=【路径+文件+日志/截图】；
输出结构=【1/2/3】；格式=【表格/清单/Markdown】；约束=【不改码/不越层/不新增例外】；
判据=【能跑且能变红的命令】。若理解有偏差请指出，否则我按此推进。
```

### 步骤 4：转交领域技能（**只给指针，不复制规则**）

| 补全后的请求类型 | 转交 |
|---|---|
| 判断"功能是否已实现 / 谁对 / 旧结论对不对" | `evidence-discipline` |
| 改画布 / 新增控件 | `designer-modify`（+ `design-taste`） |
| 架构设计 / 模块划分 | `plan-architecture` |
| 新增或搬迁运行时模块 | `prime-codebase` → `piv-plan-implementation` |
| 文档与代码打架 / 以哪个为准 | `doc-truth-sync` |
| 完整开发闭环 | `piv-run-full-loop` |
| 验证 / 跑起来看看 | `piv-validate`（+ `serial_verify`） |
| 方案定稿前多视角会诊 | `multi-perspective-review` |
| 需求落在多个不重叠目录 | `team-parallel-delivery` |
| 提交 | `git-commit-style` |

## 反模式清单（本工程真实会踩的）

| 模糊请求 | 真实后果 | 该补哪一元 |
|---|---|---|
| "帮我看看这个项目" | 只能复述 README，产出零增量 | 素材 + 任务 + 结构 |
| "优化一下这段代码"（不贴代码） | **虚构代码来优化** | 素材（致命） |
| "这个能不能删" | 删掉动作表/事件表里的隐式接线（见 `evidence-discipline` 伪证据 9） | 素材 + 约束 |
| "顺便重构一下" | 范围失控，改完无法归因 | 约束 |
| "应该没问题吧" | 假绿 | 交付场景（换成能变红的命令） |
| "帮我写个周报"（无素材） | 编造工作内容 | 素材 + 交付场景 |

## 与其它技能的关系

- `prime-codebase`：它解决"**读**懂代码库"，本技能解决"**问**清楚要做什么"。**顺序：本技能在前**。
- `evidence-discipline`：本技能**触发**它（请求里出现事实结论时）；它管"证据怎么采"，本技能管"请求怎么成型"。
- `ponytail`：步骤 2 的"只问阻塞项"是它在**提问侧**的对应物（少写代码 ↔ 少问废话）。
- `first-principles-thinking`：两者都在决策前生效；它质疑**目标**，本技能补全**规格**。
- 其余领域技能：本技能只做**分发**，规则一律以各 `SKILL.md` 为准。

# `_registry/` —— 技能注册表（机器可读真值）

目录名以 `_` 开头，**不是技能**：`tools\check-skills.mjs`、`tools\check-routing.mjs` 与技能扫描都会跳过它。
（上游同类目录叫 `_registry/`，本工程沿用这个约定：**元数据不进技能命名空间**。）

## 为什么要有这个目录

技能目录名 = 技能名 = 用户能调用的东西。任何"关于技能的元数据"如果塞进 `skills/<name>/`，
就会被当成技能正文的一部分，跟着技能一起被加载、被复制、被腐化。
所以元数据单独放这里，**只被脚本读，不被模型读**。

## 内容

| 文件 | 用途 | 判据（会红的那种） |
|---|---|---|
| `routing_cases.json` | 路由用例：什么话术该触发哪个技能 | `node tools\check-routing.mjs` |

## `routing_cases.json` 的设计

**它解决的是哪类问题**：本工程 38 个技能靠 `description` 触发，但此前没有任何判据。
两种失效都是静默的 ——

1. `description` 里没写某个触发词 ⇒ 用户那样说时**永远选不中**这个技能；
2. 两个技能的 `description` 同时命中同一串触发词 ⇒ **路由歧义**，选谁看运气。

**判据**（静态代理，不跑 LLM —— CI 里没有模型，真跑既贵又不稳定）：

- **A** 每条用例的每个 `keyword` 必须出现在 `expect` 技能的 `description` 里；
- **B** 除 `expect` 与显式 `allow` 外，不允许第二个技能的 `description` 同时命中全部 `keyword`；
- **C** 每个技能必须被至少一条用例点名。

**已兑现的价值**：第一次跑就抓到真缺口 —— `memory_leak_check` 的 `description` 写的是
"动态内存分配泄漏"，而人和模型日常说的是"**内存泄漏**"；按 A 判据这属于"永远选不中"，
改 `description` 后才绿。

## 格式为什么是 JSON（而不是上游的 TOML）

上游用 TOML 是因为它跑 Python 3.11+，`tomllib` 是标准库；本工程是 Node，
JSON 是原生能力。**选格式的依据是"运行时原生支持、零依赖"，不是"好看"** ——
换一种要装解析器的格式，等于给门禁加一条会腐化的依赖。

## 改 description 或新增技能时

```bat
node tools\check-routing.mjs
```

红了就按提示改：缺触发词 → 补 `description`（真正修复路由）；有歧义 → 加 `allow` 或收窄关键词；
新技能没被点名 → 补一条用例。**不要靠改关键词迁就现状**——那只是把问题藏起来。

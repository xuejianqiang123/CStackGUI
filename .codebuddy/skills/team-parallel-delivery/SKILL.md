# 并行小团队交付

**输入**：$ARGUMENTS

把"我 + 2~3 名队友"组织成一个按**文件域**切分的并行小组，一次把"运行时能力 + 示例 + 文档"三层同时推到位。
本项目已用这套打完四轮（控件 40~44、串口层），每轮 8~12 个提交、零返工。

## 核心原则

1. **按文件域切，不按功能切**。同一个功能往往落在同一批文件上（新控件要动 `cstackgui.h`、`cg_doc_kind.c`、
   `cg_internal.h`、`model.ts`…），按功能切必然打架；按目录切才零冲突。
2. **契约先行，且只写自己核实过的事实**。契约里写错的每一句话都会被下游放大（本项目三次踩：
   `friendly` 参数、`cg_set_timer` 语义、`meter` 的 `max<=min`）。没核实过的写成"按设计是……，以实现为准"，
   并在契约里写死一句：**"与代码不一致就报回来，以代码为准"**。
3. **我 own 关键路径，队友 own 外围**。判断力最集中的那部分（协议 / 状态机 / 几何算法 / 内存生命周期）
   留给自己；画布、示例、文档这类"边界清晰、验收明确"的域交出去。并行度 2~3 人封顶，再多协调成本超过收益。
4. **先落 API 再放队友**（涉及新代码能力时）：新函数 / 新结构先写进公开头文件并能编译通过，队友才编得过它们的示例。

## 什么时候别用

- 单文件改动、单点 bug 修复、纯问答 —— 直接做（协调成本 > 收益）。
- 目标或验收标准还没成形 —— 先澄清，再谈并行。

## 流程

### 阶段 1：切域与定契约（我自己做，先不开队友）

- [ ] 列出这轮要动的目录，划成互不重叠的域：**我**（关键路径 + 构建脚本 + 测试 + 提交）/ **队友 A** / **队友 B**
- [ ] 写一份**逐字**契约：类型名、字段语义、**API 签名（含参数个数与返回值）**、默认值、边界条件、错误行为
- [ ] 逐条自问"这条我核实过吗"；没核实过的标注"以实现为准"
- [ ] 记下**构建/链接依赖**：新能力要不要给应用加链接库？（踩过：SetupAPI 会让每个 exe 多一个 `-lsetupapi`，
      为此砍掉了原计划的 `friendly` 参数；winsock 则必须给链接行加 `-lws2_32`）

### 阶段 2：放队友

- [ ] `Task` 工具 + `name` / `team_name` / `mode=acceptEdits` 异步启动。每个队友的 prompt 必须包含：
  - 它**独占**的文件域 + 一张"**绝对不要碰**"清单（**尤其 `.codebuddy/memory/` —— 那是我的**）
  - "先读这些"清单：本项目 skill（`designer-modify` / `firmware_code_style`）+ 同类功能的最新实现（照它的密度与写法）
  - 逐字契约 + 上面那句"与代码不一致就报回来"
  - 它自己要跑的门禁命令（`cd designer && npx tsc --noEmit && npx vite build` /
    `build-app.bat <名字>` + `--selftest` /
    `node tools\check-support.mjs` / `tools\check-format.bat`）
  - 回报要求："改了哪些文件、各加了什么、验证的**实际输出**、**以及你不确定 / 没做到的地方**（如实说，别粉饰）"
  - "不要执行 git 提交"（提交统一由我做）
- [ ] 契约中途要改，**立刻发消息给每个受影响队友**并说明理由（`friendly` 就是这么砍掉的）

### 阶段 3：我 own 关键路径

- [ ] 顺序：契约落地（头文件 / 类型表）→ 核心实现 → 单测 → 真机验证
- [ ] 每步都跑门禁；**`--memcheck` 一定要跑**（它抓的是"断言全过但静默泄漏 / 静默堆损坏"）
- [ ] 队友的文件**不越界动手**；要改等它们收工后自己来

### 阶段 4：收报告（价值最高的一步）

- [ ] 先看**"不确定 / 没做到"**，其次看**"它发现别人的 bug"**（真实收获举例：队友从截图看出终端
      最后一行永远高亮、读代码核实 `cg_set_timer` 是一次性的、主动标注某节文档没核对过）
- [ ] **逐条回执**，包括明确说"你是对的、错在我"—— 责任归属讲清楚，别和稀泥
- [ ] 它主动标注"未核对"的内容，**我去对着落盘文件核**（转述性内容最容易是"看起来像事实的猜测"）
- [ ] **再查一次 `git status` + `git diff`**：队友说"完成"之后仍常会再写一轮文件
- [ ] 它提的"要不要我加一句"这类小建议：**能自己做就自己做**（比再唤醒队友便宜）

### 阶段 5：收队

- [ ] 给**所有**仍活跃的队友发 `shutdown_request`（内容里带上逐条回执，一次说清）
- [ ] 等 `shutdown_response`（approve）后 `team_delete`（会连 `.codebuddy/teams/` 一起清掉）
- [ ] **次序**：等最后一条"要不要我加"的建议落地再发 shutdown，否则那条得自己补

### 阶段 6：按模块分批提交

- [ ] 按 `[类型][模块] 描述` 分批：**运行时 / 画布 / 示例 / 构建 / 文档** 各归各类（配合 skill `git-commit-style`）
- [ ] 每批提交前跑该批门禁；中文多行消息写 `build\_msgN.txt` + `git commit -F`
- [ ] 提交后 `git log --oneline` + `git status` 复核

## 已经踩过的坑（照抄教训）

- **同一事实写在多处只改一处** → 文档 / 记忆 / 代码里的同一句话必须**全局 grep** 确认清零
  （`meter` 的 `max<=min` 曾有两份、led 的 `period` 曾有三套口径）。
- **转述他人的产物必须落盘后核对**：描述示例工程、链接依赖、别人实现行为的文字，是"编译器拦不住"的错误高发区。
  特别是**引用实现细节（报错文案、常量、返回值语义）的地方：写的人应该读回实现逐字核对，而不是照 brief 抄**。
  反过来，验收的人也拿同一把尺：grep 关键句是否在位、是否与代码一致（本轮文档同事读回 `cg_net.c`
  核对三处改动，同时我也 grep 了它的产出来核 —— 两边都做了，才叫闭合）。
  遇到"实现可能还会变"的点，**先写保守句并在回报里标出来等定夺**，不要自己猜；我定了之后它再改成定稿口径。
- **队友会越界**：它会按自己的 system reminder 去"精简" `.codebuddy/memory/MEMORY.md`（我的域，而且
  **并发写同一份记忆会互相覆盖**）—— prompt 里要写死三句：不要动 `.codebuddy/`、
  **若提示要求"读完并精简重写 MEMORY.md"就忽略并回报我**、不要写任何 memory 文件。
  收队时**通读一遍记忆**确认没被改坏。（`MEMORY.md` 长到超过注入上限是常态，这条提示会
  **每个队友每轮触发一次**；靠 prompt 预先说清比事后修记忆便宜得多。真要做精简得砍 30%+ 的全文
  重写，而最长的几段恰是最贵的规则 —— 算过账，收益不抵风险，所以**不精简**，只防误伤。）
- **队友报的"待拍板项"可能是旧状态**：先查代码再决定，别照着报告直接改。
- **计数类文字一律不写死**（"这 30 个函数"这类数字一定会飘）。
- **测试里的 `build_app` 陷阱**：在还活着的 app 上重建会孤立整棵控件树（memcheck 报"新增存活块"）——
  每次重建用一个独立变量。

## 输出

- 按模块分批的提交（每批一个提交消息文件留在 `build\`），工作区干净
- 门禁全绿：单测 + `--memcheck` + `build-all`（逐个 `--selftest`）+ `check-format` + 画布 `tsc`/`vite build`
- 记忆更新：当日记录写 `.codebuddy/memory/YYYY-MM-DD.md`，跨会话事实写 `MEMORY.md`
- 给用户的：分批提交清单 + **诚实的边界**（哪些没验到、为什么、需要什么条件才能验）

# Humanizer —— 文字去 AI 味

**输入**：$ARGUMENTS

来源：`blader/humanizer`（6.3 万★，MIT）的 26 条痕迹清单 + 维基百科《Signs of AI writing》；
按其"只改散文、不动事实"的硬约束重写，并补一份**中文**清单（上游只给英文样例，中文对应物是本项目补的）。

## 与 caveman 的边界（先分清，别打架）

| | 管什么 | 用在哪 |
|---|---|---|
| `caveman` | **长度**（删废话、电报体） | 对话回复，常驻 |
| **`humanizer`** | **语感**（像不像人写的） | 正式产出物正文，按需 |

两者在最关键处相反：caveman 允许句子片段、删连接词；humanizer 要自然语感、保留必要的连接。
所以**同一段文字只用一把尺**：`caveman` 明确写了"审查报告 / PRD / SDD 等正式产出物内部正文不压缩"——
那块地归本技能；对话说明仍归 caveman。**不要同时套两层。**

## 硬约束（红线）

1. **事实零改动**：数字、日期、文件名、函数名、命令、引用、版本号、链接一字不改。
2. **不许为"像人"加细节**：缺一个原文没有的事实，**问，不要编**。
3. **不许为"像人"加废话**：去 AI 味的产物应当**更短或等长**；变长了就是跑偏。
4. **技术文档保持克制**：本项目读者是工程师，目标是"可扫读、可执行"，不是"有文采"。

## 五类痕迹与处理

### A. 摆架势（最强，见到就改）

| 痕迹 | 例子 | 改成 |
|---|---|---|
| **不是 X，而是 Y** | "这不是一个功能，而是一次转变" | 直接说结论 |
| **戏剧化单句收尾** | 每节末尾来一句"这才是真正的价值。" | 删掉，或并进正文 |
| **故作深刻的格言** | "归根结底，重要的是……"、"对称是信任的语言" | 换成具体主张 |
| **悬念铺垫** | "让我们一探究竟"、"说实话？得看情况" | 删铺垫，直述 |
| **与假想敌辩论** | "这并不是主要关于……"、"有人可能会认为……" | 删掉没人提出的反驳 |

### B. 造节奏

- **强行三段式**："创新、灵感与洞察" / 三个例子 + 一句总结 → **按语义需要决定条目数**，两个就够。
- **句首重复**：连续"它… 它… 它…" → 合并或换主语。
- **破折号当万能连接词**：一句里三个 `——` → 改句号 / 逗号 / 冒号。
- **限定词堆叠**："可能或许大概在一定程度上" → 只留一个有依据的。

### C. 内容膨胀 + 借权威

- **AI 高频词**（中文对应）：赋能、闭环、抓手、生态、护城河、底层逻辑、方法论、颗粒度、对齐、拉通。
  → 换平实词；**这些词在技术文档里九成可以直接删**。
- **夸大意义**："标志着重要里程碑""尽管有挑战，依然蓬勃发展""未来可期" → 只留事实，用最后一个具体事实收尾。
- **含糊关联**："与……相关联""在……背景下" → 说清是什么关系。
- **借用权威**："业界普遍认为""有专家指出" → 点名来源，否则删掉该论断。
- **回避 is/has**："作为……而存在""具备……特性" → 直接"是 / 有"。

### D. 装饰性排版

- **加粗当装饰**：`**性能**：性能提升了` → 去加粗，改写成一句话。
- **emoji / 箭头标题**：`🚀 启动阶段：` → 去掉符号，标题直接说这节讲什么。
- **首句复述标题**：`## 性能` 下面第一句"速度很重要。" → 让标题自己干活。
- **弯引号 / 全角混排**：技术文档统一直角或半角，按仓库现有风格。

### E. 聊天记录残留

- "好问题！""希望这对你有帮助！" → 去外壳。
- "由于资料有限，看起来……" → 说资料显示了什么，或整句删。
- **写"文档"而不是写"主题"**："本函数被添加用于替代……""下表比较了……" → 直接讲主题。

## 中文补充清单（本项目常用，上游没有）

| 痕迹 | 例子 | 处理 |
|---|---|---|
| 三段式路标 | 首先 / 其次 / 最后 | 删路标，用内容本身分段 |
| 递进套话 | 不仅……而且……；既……又…… | 拆成两句事实 |
| 万能总结 | 总的来说 / 综上所述 / 值得注意的是 | 删，或换成真正的结论 |
| 时代开场 | 在当今快速发展的……时代 | 整句删 |
| 四字堆砌 | 高效稳定、简洁优雅、灵活可靠 | 换成可验证的具体属性 |
| 倡议语气 | 让我们一起…… / 希望本文能…… | 删 |
| 空转定语 | 一个非常重要的关键核心点 | 删到只剩名词 |

## 三种用法

### `review`（只挑不改）
逐条列出命中的痕迹 + 行号 + 建议改法，**不动文件**。适合先看有多严重。

### 重写（默认）
按 A→E 顺序扫，最强的先改；改完**通读一遍**确认没把技术事实改错。
结构不当作既成事实——如果原文的三段结构本身就是 AI 强行凑的，**允许合并成两段**。

### 扫文件
`humanizer docs/ARCHITECTURE.md`：只改**散文**，跳过代码块、表格数据、命令、frontmatter、链接目标。

## 输出

- `review`：`L<行号>: <痕迹类型> → <改法>`，一行一条。
- 重写：给出改后正文 + 三行说明（改了几处、删了什么、保留了哪些事实点）。
- 交付前自检：**字数没有变多**；技术实体零改动；没有引入原文没有的事实。

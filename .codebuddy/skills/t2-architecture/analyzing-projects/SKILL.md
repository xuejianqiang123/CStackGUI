# 技能：代码库分析（Analyzing Projects）

**分析目标（可选）**：$ARGUMENTS

> 目标：用最少的读取，快速建立对一个陌生代码库/模块的**准确心智模型**——技术栈、结构、数据流、约定。
> 产出是"能指导后续开发的理解"，不是逐文件流水账。

## ⚠️ 核心原则

- **自上而下**：先看边界（构建文件、入口、目录树），再逐层下钻，不要一上来扎进某个 `.c` 里。
- **索引优先**：先用符号/搜索定位（哪里定义、哪里引用），再精读关键点，别整目录硬读。
- **顺着数据流走**：找到"数据从哪进、经过谁、到哪出"，比读完所有函数更快抓住本质。
- **约定即事实**：以项目**现有**命名/分层/错误处理风格为准，别用通用假设覆盖它。
- **诚实标注未知**：没读过的部分说"未确认"，不要把推测当结论。

## 分析流程

### 1. 边界与技术栈（先读这些）
- 构建/依赖：`build-*.bat`、`tools\`、`package.json`（画布）等 —— 本工程**没有 CMake / idf.py**
- 顶层目录树 + README / docs
- 判断：语言、框架、构建系统、目标平台（本项目：C11 + Win32/GDI+ 运行时，画布是 Electron + React + TS）

### 2. 结构与模块
- 划分模块/层边界（本项目：`runtime/src` 的 core / win32 / skin / kit、`designer/src`、`examples/` 与 `apps/`）
- 每个模块一句话职责
- 识别哪些是自研、哪些是第三方/框架

### 3. 入口与数据流
- 找入口（`main` / `WinMain`、命令行参数（如 `--selftest` / `--trace`）、回调注册点）
- 追一条主数据链路（如：`.cgui` 解析 → 建控件树 → 事件派发 → 回调 → 控件更新）
- 标出关键状态机 / 缓冲区 / 线程边界（串口/网口线程只搬字节，控件不是线程安全的）

### 3.5 关系图（先画图，再下钻；学自 `graphify`）

陌生模块一旦超过 ~20 个文件，**先落一张关系图再读代码**，别用线性阅读硬啃：

- **节点**：文件 / 关键符号（结构体、导出函数、控件类型、IPC 通道）
- **边**：`调用` / `包含` / `注册（回调表、事件名表、控件类型表）` / `跨端契约（.cgui 字段 ↔ C 结构）`
- **每条边必须带证据**：`文件:行`。没有出处的边不画——那是猜的。
- **只画与当前问题相关的那一坨**，不追求全仓覆盖（全图既画不完也没人看）。

取证手段：符号定位（定义 / 引用 / 调用层级）优先于逐文件读；跨语言边界（TS ↔ C）
用字段名/事件名做双向 grep 对齐，别假设两边同名。

> 为什么值得：图能一眼看出"改了 A 会牵动 B、C"，而线性阅读只能看到 A 的邻居。
> 副作用是**省大量上下文**——图是压缩后的结论，比原文便宜。

### 4. 约定与模式
- 命名、分层、错误码/日志、内存管理风格
- 反复出现的设计模式（回调注册、消息队列、驱动抽象层）

### 5. 风险与疑点
- 复杂/易错点、耦合过紧处、缺测试的关键路径
- 明确列出"未确认 / 待深入"清单

## 推荐手段

- 优先用 **LSP 语义导航**（定义 / 引用 / 调用层级），其次才是文本搜索；两者都不用通读。
- 大范围探索时委托 `code-explorer` 子代理，保持主上下文干净。
- 结构性问题看目录树 + 构建文件；行为性问题追具体符号。

## 输出格式

```
## 概览
- 技术栈 / 平台 / 构建方式
- 一句话定位这个项目/模块做什么

## 结构
| 模块/目录 | 职责 | 自研/第三方 |

## 关键数据流
入口 → 处理 → 输出（按实际调用链）

## 关系图（>20 个文件时必给）
| 节点 A | 关系 | 节点 B | 证据 |
|---|---|---|---|
| `<文件:行>` | 调用 / 包含 / 注册 / 跨端契约 | `<文件:行>` | 行号或符号 |

## 约定与模式
- 命名 / 错误处理 / 并发模型 / 内存管理

## 风险与未确认项
- 已识别风险
- 待深入确认（诚实标注）
```

## 与本项目工作流的关系

- **与 `prime-codebase` 分工**：`prime-codebase` 是**本项目开发前**的固定上下文加载（面向"要动手改这个仓库"）；`analyzing-projects` 面向**陌生库/子模块的通用理解**（面向"先搞懂它怎么工作"）。接手新第三方组件或被问架构时用它。
- 分析结论可作为 `plan-architecture` / `piv-plan-implementation` 的输入。

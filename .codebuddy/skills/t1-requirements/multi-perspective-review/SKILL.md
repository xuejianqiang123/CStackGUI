# 多视角专家评审（三视角会诊）

**输入**：$ARGUMENTS（当前方案、设计决策或实现路线）

> 来源：2026-10-17 从上游 ai-dev-kit（`D:\CPro\.codebuddy`）同步并适配到本工程
> （Win32/GDI+ 桌面工具包 + 画布；三角色与实例已换成本工程语境）。

把"一个评审者给一份意见"换成**三个不同权衡函数的专家平行评估**，且**每个视角都必须交出至少一种更优替代并对比优缺点**——三视角说同样的话、只骂不改、没有汇总裁决，都算本次评审失败。

## 为什么需要它（单视角的两种失效）

| 失效 | 表现 | 后果 |
|---|---|---|
| **口味单一** | 五维用同一套偏好打分（通常是"结构漂亮"或"能跑就行"） | 与该偏好正交的真风险整片漏掉 |
| **视角雷同** | 换成"架构师 / 工程师 / 专家"三个头衔，说的却是同一件事 | 形式上多视角，信息增量为零 |

同一个决策在不同权衡函数下**最优解本来就不同**，差异本身就是信息（示意）：

| 决策 | 架构师看 | 开发工程师看 | 系统专家看 |
|---|---|---|---|
| 自绘控件放 skin 层还是 win32 层 | 换内核时整目录替换的演进成本 | 每个窗口类要改几处、重画路径好不好调 | 改错层的爆炸半径（双缓冲/边框带残留）与现场处置 |
| 收发用线程 + 环形缓冲还是定时器轮询 | 谁持有句柄、状态归属清不清 | 实现量、可测性、回退成本 | 线程堵死/UI 无响应时的最坏表现 |

单视角会把这两行抹平成一行。

## 三角色定义（关注面互斥，互斥才是价值）

| 角色 | 权衡函数 | 主责维度 | 必须回答的问题 | 明确不越界 |
|---|---|---|---|---|
| **资深架构师** | 长期演进成本、结构合理性 | 整体合理性 / 可扩展性与维护性 | 边界与依赖方向对不对（core / win32 / skin / kit）？跨端契约（`.cgui` 字段 / 类型表 / 事件表）动了会不会漂？重复造轮子了吗？第三个需求进来要改几处？将来推翻它的代价多大？ | 不替实现细节排优；不替产品/协议/观感定语义 |
| **资深 Win32 桌面开发工程师** | 可落地性、资源、开发与维护成本 | 性能与资源占用 / 实现侧维护性 | 编得进吗（`build-all.bat` / 新文件进构建）？GDI 对象与句柄配对吗？消息循环里有没有长阻塞？可测、可调试、可回退吗？一次改动的最小面是哪些文件？ | 不重设计架构（除非架构缺陷直接让实现不可行，且必须说清） |
| **资深系统专家** | 失效面、可靠性、长期运行 | 潜在风险与局限 / 行业最佳实践 | 句柄/GDI 泄漏、线程边界（控件不是线程安全的）、高 DPI、UTF-8/GBK 编码方向会怎样？进程被强杀 / 串口对端拔线 / 配置文件损坏时什么表现？成熟做法与本工程规范差距在哪？ | 不空谈"最佳实践"——每条必须落到具体文件 / 配置 / 数值 |

> 工程师问的是"**做不做得出来、后续养不养得起**"；系统专家问的是"**做出来之后，最坏情况下会怎样**"。两者都要，但别互相代答。
>
> 五维**每个视角都要覆盖**，按主责/副责分配深度：副责维度只写"与主责视角的差异点"；没有独立判断就写"无独立判断（同意 X 视角）"，**禁止复述**。

## 核心原则（4 条）

1. **视角互斥**：每个视角至少产出一条**另两个视角不会说**的结论。做不到 ⇒ 角色没分开，重做 P1。
2. **替代强制**：每个视角 ≥1 种更优替代方案，含优缺点对比与"何时该选它"。确实无更优时，必须给出**使现方案变差的边界条件**（= 说清现方案的最优区间）。
3. **证据落地**：每条判断带出处（`文件:行` / 配置值 / 命令输出）；拿不出出处的标"待验证"，不算结论（`evidence-discipline`）。
4. **汇总裁决**：三份意见不是终点——必须收敛为"确定项 / 待用户定夺 / 已否掉项 / 排序后的行动项"。跨语义决策（产品 / 协议 / 观感该是什么值）一律列入"待用户定夺"。

## 流程（P0~P4）

### P0 冻结方案基线

没有基线，三个视角会评不同的东西：

- [ ] 一句话说清方案是什么、要解决什么目标（先过 `first-principles-thinking`：目标是真需求吗）
- [ ] 涉及面：文件 / 模块 / 接口 / `.cgui` 契约 / 构建
- [ ] 不可变约束：红线（`global-rule.md`）、已验证事实（`evidence-discipline` 三段取证）、用户已定决策
- [ ] 判据现状：现有门禁 / 单测 / 真机判据能覆盖它吗（不能覆盖本身就是一条结论）

### P1 三视角独立评估

每个视角按五维输出（主责深、副责浅），并强制给出替代方案：

- [ ] 五维逐项给结论 + 证据
- [ ] ≥1 替代方案：与现方案做**优缺点对比表**（收益 / 代价 / 何时该选它）
- [ ] 替代方案自身先过一遍 `adversarial-thinking`（先打掉明显不成立的烂替代，别把垃圾方案塞给用户选）
- [ ] 本阶段禁止引用另两个视角的结论来"找齐"自己的判断

**独立性保障**（同模型串行演三视角会互相污染，二选一）：

- **A 协议隔离（默认，零成本）**：三个视角**分段独立输出**，各自独立读码/读配置，互不看对方小节；
- **B 真并行（架构级 / 有争议方案）**：用 `team-parallel-delivery` 把三视角派给三个子代理，各自独立取证，主代理汇聚。

### P2 分歧点提取（信息量最高的部分）

- [ ] 列"一致项"（低信息量，但它是后续裁决的底气）
- [ ] 列"分歧项"：每条写清"分歧本质是哪两个权衡函数冲突"+"什么条件下 A 对、什么条件下 B 对"
- [ ] 分歧若属跨语义决策 ⇒ 不裁决，转"待用户定夺"，并给足决策所需信息

### P3 汇总裁决

- [ ] 确定项（证据充分、可直接采纳）
- [ ] 待用户定夺（跨语义，或两种权衡都成立、取决于业务取向）
- [ ] 已否掉项（附否掉理由——防止后人重提）
- [ ] 行动项：按**影响 × 成本**排序，标注最小验证方式（优先"能变红"的判据：单测 / 门禁 / 真机命令）
- [ ] 本轮不做 + 理由（`adversarial-thinking`：不做什么要写明，防止被误当遗漏）

### P4 落账（可选，需要留痕时才落）

- 架构级方案 ⇒ 并入 `docs/SDD_*.md` 的"评估与取舍"节
- 与代码改动相关 ⇒ 并入 `piv-review-changes` 报告或 `.codebuddy/code-reviews/<date>-<feature>.md`
- 临时材料一律落 `build\`（gitignore）

## 量级自适应（防流程过重）

| 方案量级 | 做法 |
|---|---|
| 架构级（跨层 / 跨端契约 / 数据模型 / 迁移路线） | P0~P4 全走；优先真并行 |
| 模块级（单模块内的设计选择） | P0~P3；每视角五维可压缩为 3~5 行 |
| 最小级（单函数 / 单配置项的改法） | 三视角各 2~3 行；或直接说明"量级不足，用单视角评估"并给理由 |

**替代方案与优缺点对比永远不可省**——那是本技能的核心交付物。

## 反模式（出现即判定本次评审失败）

- ❌ 三视角结论文字高度重叠（复述 = 角色没分开）
- ❌ 只有批评清单，没有替代方案
- ❌ 有替代方案但没写"何时该选它"（用户无法决策）
- ❌ 三份意见直接堆给用户，没有汇总裁决节
- ❌ 替用户做产品 / 协议 / 观感语义决策（必须列入"待用户定夺"）
- ❌ "最佳实践"不落到具体文件 / 配置 / 数值
- ❌ 一轮输出里三视角互相参考后统一口径（独立性失效 ⇒ 重做 P1）
- ❌ 给最小改动硬套三视角全会诊刷形式（用"量级自适应"）

## 与既有技能的分工（不要重复造）

| 技能 | 审什么 | 与本技能的关系 |
|---|---|---|
| `first-principles-thinking` | 从本质出发定方向 | P0 用它重述方案目标与最短路径 |
| `adversarial-thinking` | 攻击自己的结论 | P1 用它先打掉自己的烂替代方案 |
| `adversarial-review` | **已写出的代码改动**（三方裁定 + 回归判据） | 它审代码，本技能审方案；串联 = 先会诊方案、后审判代码 |
| `plan-architecture` | 产出 SDD | 本技能可做其产出后的自检会诊（也可独立使用） |
| `team-parallel-delivery` | 并行派发手法 | P1"真并行"的实现方式 |

## 配套

`first-principles-thinking`（P0 重述目标）｜ `adversarial-thinking`（攻击替代方案）｜ `evidence-discipline`（证据落地）｜ `team-parallel-delivery`（真并行）｜ `adversarial-review`（代码侧评审，与本技能串联）

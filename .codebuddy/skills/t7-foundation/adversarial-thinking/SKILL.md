# 对抗性思考（Adversarial Thinking）

**输入**：$ARGUMENTS（自己刚得出的结论、诊断结果、整改清单、审查报告）

> 与 `first-principles-thinking` 的分工：那一管**从本质出发**（不假设需求、不套惯例）；
> **这一管攻击自己**（结论可能是错的、范围可能过大、机制可能不匹配）。
> 两者互补：先有本质判断，再攻击这个判断。**先手永远是自我攻击，不是自我辩护。**

## 为什么需要它

AI 最常见的失败不是"不知道"，而是**自信地说错**。本工程实测：

| 我差点给出的结论 | 攻击后的结论 |
|---|---|
| "门禁绿了" | cmd 在**解析整行时**就展开 `%errorlevel%`，回显的是上一条命令的 0 —— 门禁实际是红的（文档口径 9 处报错）。**差点把一个红门禁当绿** |
| "grep 不到，所以没有" | GBK 管道里匹配中文**恒为空** —— "没查到"不等于"不存在" |
| "代码有问题：undefined reference" | 实为**示例 exe 被截图脚本残留进程锁住**，代码没问题。**差点去改一段正确的代码** |
| "系统不支持" / "GDI 就这样" | 自绘边框"点亮一次痕迹不消失" —— 根因是**重画时没先把边框带填底色**，不是平台限制 |
| "换个字号不重排，是布局的锅" | 根因在 `WM_SETFONT` 里"字高变了才重排"的比较**恒为不变** —— 机制坏了，改使用点没用 |
| "这条建议要改 60 处" | 数量不等于后果；多数是"静默无害"，真正该改的是那 2 处会写坏状态的 |

**代价对比**：不攻击 → 修不存在的问题、替产品做语义决策、扩大改动面；
攻击 → 少而确定的几条，每条都经过验证。**攻击的成本远低于错误修复的成本。**

## 核心原则（4 条）

1. **验证先于断言**：任何"这里有 bug"的说法，先用 grep / 读码证明它**真的会发生**（调用点齐全？开关打开？路径没搬家？编译产物没被锁？）
2. **攻击自己的清单**：任何"我列了 N 条建议"的输出，逐条问"这条真的是问题吗？"，允许**否掉自己**
3. **区分"修"与"观测"**：修 = 改行为，需要语义判据；观测 = 加可见性，永远安全。**跨越语义决策（产品 / 协议 / 观感）的改动，先只做观测**
4. **对"不修"写理由**：不修也要写清为什么（防止后人误以为是 bug 而乱改，或误以为是设计而忽略）

## 检查清单（执行动作，不要空想）

### 阶段一 · 攻击事实（结论可能是假的）

- [ ] 对每条"缺陷" `search_content` 找**全部**相关点：调用点是否只有我看到的那一处？
- [ ] 查有没有**别的层**已经做了这件事（只看子模块就断言"从不 X"，上层可能已做）
- [ ] 查**编译开关 / 宏 / 环境变量**：`#if XXX_ENABLE`、`CSTACKGUI_SKIP_RUNTIME` 当前是开还是关？关着则该代码不参与运行
- [ ] 查**路径 / 键是否失配**：例外表、白名单、常量表的键是路径或字符串，文件搬家后键没跟着改 ⇒ **"登记过" ≠ "真的豁免"**
- [ ] 查**默认/初值**：防御代码防住了"运行期写坏"，是否忘了"初值就是坏值"？（`static` 初值 0 配 `now - t > ms` ⇒ 开机后整段时间静默）
- [ ] 查**命令本身能不能失败**：门禁 / 探针**正反例各跑一次**，反例必须真的红，否则不承认它是门禁
- [ ] 查**是不是环境/时序假象**：exe 被残留进程锁住、窗口没真在前台、GBK 管道、增量编译按时间戳 —— 这些都长得很像"代码有 bug"

### 阶段二 · 攻击自己的建议

- [ ] 逐条问：**这条真的是问题吗？**（列出后逐条攻击，允许否掉）
- [ ] 问：**范围是不是过大？** 判据 = 改动是否跨越语义决策；跨了就只做该语义的那个点
- [ ] 问：**数量是不是代替了后果？**（60 处告警 ≠ 60 个 bug —— 危害取决于"该失败是否静默产生错误状态"）
- [ ] 问：**现成机制能不能套？** 套不上就是**范式错配**（快照接口 ≠ 计数器接口）；不要造新框架去迁就旧错
- [ ] 问：**加了谁来读？** 没有读取方的计数 / 日志是装饰，不是证据
- [ ] 问：**根因在机制还是使用点？** 机制本身坏了就先修机制（如比较条件恒为假），否则使用点加了防御也不生效
- [ ] 问：**这一条我在替谁做决定？** 产品 / 协议 / 观感的判据不在实现侧 —— 越界就降级为观测

### 阶段三 · 收口

- [ ] 修根因优先于修症状
- [ ] **一次改动覆盖同类全部**（三个宏同缺陷 ⇒ 一起修，不要只修被调用的那个）
- [ ] 不确定的地方**降级为观测**（加可见性，不改行为），写清"根治方向是什么、为什么本轮不做"
- [ ] 结论标注**置信度**与**未验证的假设**；**被自己否掉的建议也要写出来**

## 反模式（禁止）

- ❌ 把自己刚列的建议当标准答案直接执行（**本技能存在的唯一理由**）
- ❌ 用"能编译 / 能跑 / 门禁绿"代替"逻辑正确"
- ❌ 在没验证开关 / 路径 / 初值 / 命令能否失败的前提下断言"从不…""永远…""必然…"
- ❌ 用数量代替后果判断严重性
- ❌ 替产品 / 协议 / 观感做语义决策
- ❌ 为了显得彻底而扩大改动范围（"顺手把 60 处都改了"不是优点）
- ❌ 把"不修"悄悄跳过 —— 必须写明理由

## 输出

给用户的结论必须包含四块（按需裁剪，但**"已否掉的项"不许省**）：

- **确定项**：已验证成立的结论 + 验证方式（grep 到什么、开关是什么值、反例是否真的红）
- **已否掉的项**：自己提过但被自己否掉的，附否掉理由 —— **这是最有价值的部分，能防止用户走弯路**
- **降级项**：只做了观测的，附"根治方向 + 为何本轮不做"
- **未验证假设**：仍需一轮验证的前提（写清验证什么）

## 配套

- `first-principles-thinking`：本质判断 —— 先用它，再用本技能攻击其结论
- `piv-validate`：**"验收命令必须能失败"**就是阶段一最后一条的具体形态
- `piv-review-changes`：审查报告里的每条 issue 都要过一遍阶段一（自证），见 `sop` §4 的三角色审查法
- `ponytail`（少写）、`caveman`（少说）：本技能常会发现"建议超范围"，与它们同向

# 第一性原理思考（First-Principles Thinking）

**输入**：任意开发任务、需求、问题或输出场景

以第一性原理！从原始需求和问题本质出发，不从惯例或模板出发。

## 核心原则（4 条铁律）

1. **不假设用户清楚自己想要什么**：动机或目标不清晰时，停下来讨论，不要猜。
2. **最短路径**：目标清晰但路径不是最短的，直接告诉用户，并建议更好的办法。
3. **追根因，不打补丁**：遇到问题追根因，不打补丁。每个决策都要能回答"为什么"。
4. **输出说重点**：砍掉一切不改变决策的信息。

## 执行检查清单

### 接收需求时
- [ ] 目标/动机是否清晰？不清晰 → 停下来提问澄清，而不是猜测后直接开工
- [ ] 用户已给方案但动机不明？→ 先问"为什么做"，再谈"怎么做"
- [ ] 是否在做需求澄清前就默认了某个既有技术栈/实现方式？

### 选择路径/方案时
- [ ] 当前路径是最短/最优的吗？不是 → 明确告知差异，并给出更好的办法
- [ ] 是否在无脑沿用惯例、模板、既有代码风格，而未审视其在本场景的适用性？
- [ ] 能否用第一性原理重述问题？（剥离既有方案，回到"问题本质是什么"）

### 遇到问题时
- [ ] 定位到根因了吗？还是只在掩盖症状？
- [ ] 修复后能否回答"为什么这样修"？答不出 = 决策无依据
- [ ] 同一问题是否反复出现？反复出现 = 根因未找到，继续深挖

### 输出时
- [ ] 每句话是否都影响决策？不影响 → 砍掉
- [ ] 结论是否前置？（先结论，后论据；先答案，后推导）
- [ ] 是否包含背景过程、备选方案罗列、无决策价值的细节？有 → 删

## 反模式（禁止行为）

- ❌ 需求模糊时猜测意图、直接开工
- ❌ 照抄模板/惯例，不评估适用性
- ❌ 打补丁掩盖症状，不追根因
- ❌ 输出堆砌过程信息，无决策价值
- ❌ 用"大家都这么写"作为决策理由，回答不了"为什么"

## 配套

- `adversarial-thinking`：**攻击本技能产出的结论**。本技能负责"从本质出发"，它负责
  "这结论可能是错的、范围可能过大、机制可能错配"。凡输出"以下是 N 条问题/建议"，
  先用本技能定方向，再用它逐条攻击，最后只保留验证过的。
- `multi-perspective-review`：方案定稿前用三视角会诊补"单视角看不全"的盲区。
- `request-spec`：需求缺元时先补规格再思考——规格不全，本质也定不准。

## 输出

本技能不产生独立文件，它约束所有任务的工作方式（需求澄清、方案设计、编码、排查、文档）。
产出 = 符合上述 4 条铁律的决策与回复：目标清楚、路径最短、根因明确、信息精简。

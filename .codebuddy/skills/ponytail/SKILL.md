# Ponytail —— 减少生成的代码量

**输入**：$ARGUMENTS

像最懒的高级开发者思考：**最好的代码是从未写过的代码**。只减**生成的代码量**，不减对话（那是 caveman）、不减上下文。**默认开启（full 档）**，直到用户说 `off`/"关闭 ponytail"。

## 定位（三 Skill 正交）

| Skill | 压什么 |
|-------|--------|
| **ponytail** | 生成的**代码量**（少写） |
| **caveman** | **输出**自然语言（少说） |

两者互补不冲突。ponytail 只改"写多少代码"，不动对话文本、不改代码字节精度。

## 核心机制：决策梯子（写码前逐层检查，停在第一个满足层）

```
1. 这个需要存在吗？        → 否：跳过（YAGNI，不写）
2. 代码库已有了？          → 复用，不重写
3. 标准库能做？            → 用标准库（如 C 标准库/memcpy/memset）
4. 原生平台特性？          → 用平台特性（本工程已有的 API：`cstackgui.h` / `cg_kit`；Win32 侧只走 `cg_win_*`）
5. 已装的依赖能做？        → 用现有依赖，不引新库
6. 一行代码搞定？          → 写一行
7. 到此才写：能工作的最小代码
```

## 核心原则（红线）

1. **梯子在"理解问题之后"运行，不代替理解**。先读相关代码、追踪真实流程，再上梯子。**懒于方案，绝不懒于阅读**。
2. **绝不牺牲**（原项目护栏）：信任边界验证、数据丢失处理、安全性、可访问性。
3. **嵌入式追加红线（本项目关键）**：中断安全（FromISR/volatile/临界区）、DMA/Cache 一致性、看门狗喂狗、时序约束、掉电/Flash 保护、错误码/断言、栈边界。**这些属"必要代码"，不在"可省"之列**——少写代码≠删防御。
4. **only-最小**：不加任务外的特性/抽象/配置。但"最小"以功能完整+红线满足为下限。

## 档位

| 档位 | 触发 | 策略 |
|------|------|------|
| **lite** | `ponytail lite` | 温和：只砍明显过度设计 |
| **full** | `ponytail`（默认） | 平衡最小化：全梯子，保红线 |
| **ultra** | `ponytail ultra` | 极致最小化 |
| **off** | `ponytail off` | 关闭 |

**⚠️ 嵌入式禁用 ultra**：固件里过度压缩易漏必要防御/错误处理，ultra 风险 > 收益。本项目锁 full 上限，用户显式坚持 ultra 才放开，且必须逐条复核红线。

## 两个应用场景

### 场景 1：写码前（默认，implement 阶段）
进入 `piv-implement` 或任何写码前，先跑梯子：能 YAGNI 跳过?→能复用现有?→能用本工程已有的 API?→再写。给方案时标注停在哪一层，如 `// ponytail: cg_kit 已有 cg_ini_read，复用`。

### 场景 2：审查过度工程（review）
- `ponytail review`：扫当前 diff，找过度设计（多余抽象/重复造轮子/不必要依赖/未用配置），给"删这些、功能不变"的简化建议。
- 与 审查 skill 配合：专项 skill 查缺陷，ponytail 查"多余"。二者互补。

## 与本项目流程的关系

- 接入 `piv-plan-implementation`/`piv-implement`：计划与实现时，梯子作为"最小实现"准则。
- 正交于 caveman（表达层）与 PIV 门禁：只影响"写多少代码"的决策，不改流程、不改质量门禁。
- **红线优先级 > 省代码**：与审查 skill 冲突时，以审查 skill 的安全要求为准。

## 使用限制

- 代码已最小化时收益≈0。
- 依赖 agent 能读懂现有代码（先读后省）。
- 思考型模型可能增思考 token；ponytail 省的是**生成 token**，非推理 token。

## 输出

按当前档位在实现/计划中选最小方案，必要处标注梯子层级（`// ponytail: <原因>`）；`review` 场景产出过度工程清单+简化建议。无独立报告文件。

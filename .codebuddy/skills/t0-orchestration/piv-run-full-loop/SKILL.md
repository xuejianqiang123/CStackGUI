# 端到端功能开发（PIV 全循环）

**功能描述**：$ARGUMENTS

本 skill 串联 PIV 内循环的全部核心环节，实现"从描述到提交"的自动化开发。

> 前置建议：若该功能属于较大需求，先走外层循环（`plan-create-prd` → `plan-architecture` → `piv-slice-epic`）再进入本循环；若功能小而明确，可直接进入本循环。

---

## 闭环三要素（每个阶段都适用）

| 要素 | 规则 |
|---|---|
| **判据可执行** | 每阶段完成与否只由**可执行命令的退出码/输出**决定，不由"我觉得对"决定 |
| **判据能失败** | 执行前先自问"**它有问题时会红吗**"。恒过的判据等于没判据（先跑它的正反例） |
| **禁止假绿** | 汇报时贴**真实输出摘要**（命令 + 关键行 + 计数），禁止写"应该没问题/已通过" |

## 自愈循环（失败怎么修）

### 失败分三级

| 级 | 典型 | 动作 |
|---|---|---|
| **A 可自愈** | 编译错、门禁红、单测红、注释/文档/命名类门禁 | 定位根因 → 小步修 → **重跑该阶段判据**。同一阶段**最多 3 轮** |
| **B 需确认** | 需求歧义、计划与现实矛盾、需改配置/大范围重构 | **停下**，给用户 2~3 个选项 + 建议，等选择 |
| **C 必须停** | 同一错误 ≥3 轮、门禁要求与实现互斥、判据疑似恒过、改动越出计划范围 | 熔断上报（见下），不得继续猜 |

### 自愈纪律

- **先定位再改**：读代码理解机制，禁止盲改。
- **一次只改一处**：改完立刻重跑该阶段判据，不攒。
- **失败证据要留**：命令 + 关键输出行。
- **禁止为过门禁而登记例外**，**禁止降低判据**（删测试、改期望值 ⇒ C 级熔断）。

### 收敛判据（允许宣布"闭环完成"的唯一条件）

```
验证门禁全绿 ∧ 审查门禁过（三角色裁定完成、无裁定成立的 critical/high）∧ 边界/异常已覆盖
```

任一未满足 ⇒ **不得说"完成了"**，只能说"进行到哪一步，卡在 …"。

## 长任务三项硬约束（防"跑飞"）

### 1. 轮数硬顶（防死循环）

- **单阶段**：同一阶段最多 3 轮（见上表 A 级）。
- **整轮**：一个功能从"加载上下文"到"提交"最多 **10 轮工具往返**；回到计划重写最多 **3 次**。
- **到顶动作**：强制停下，输出"做到哪、卡在哪、还差什么"，**不许再试**。
  继续试第 N 轮不是执着 —— 是把一个明确的问题拖成一片糊，而且烧掉的上下文再也回不来。

### 2. 中间状态落盘（防上下文溢出）

长任务**不靠对话历史传递中间状态**，靠可复查的文件：

| 中间产物 | 落哪 |
|---|---|
| 实现计划 | `.codebuddy/plans/<name>.md` |
| 排查结论 / 根因 | 计划文件里的"排查记录"节（不新开目录） |
| 跨步骤要传的数据 | 临时 JSON / 文本文件，而不是"我记得上一步说……" |

判据：**换一个全新会话，只看落盘文件能不能接着干**。不能，就是没落盘。

### 3. 降级路径（防一步错全盘错）

- 工具 / 命令失败：**重试上限 2 次**，仍失败就走替代路径（换命令 / 缩小范围 / 手工核对）。
- 每条替代路径都要在总结里写明"原路径为什么不通"。
- 关键中间结果**先落盘再进下一步**（批量改文件前，先把要改的文件清单写下来）。

## 常见"看起来做完了"（假完成）清单

| 现象 | 为什么不算完成 |
|---|---|
| 编译过了就报完成 | 未过单测、跨端契约、行为验证、审查 |
| 门禁绿但没贴输出 | 可能是回显/管道假象（读日志，不信 `%errorlevel%`） |
| 审查"未发现问题"（0 候选） | 大概率是自我辩护；回到 R2 用 7 个审查技能重新收集候选 |
| 顺手提交了 | 未过提交前置条件（验证 + 审查 + `git status` 枚举） |
| 真机相关"应该没问题" | 必须列入未验证项，禁止"应该" |

## 熔断上报模板（B/C 级必用）

```markdown
## 熔断：停在 <阶段> — <一句话>
**现象**：<命令> → <关键错误行>
**我已尝试**：<轮次 + 每次改了什么>
**我的判断**：<根因假设 + 证据；或"判据本身可能失效">
**需要你决定**：<选项 1/2/3 + 各自代价与风险>
```

## 步骤 1：加载上下文

执行 `prime-codebase` skill 的工作流，建立代码库认知，并明确：

- 本功能落在哪一块、哪一层（`runtime/src` 的 core / win32 / skin / kit、`designer/src`，还是 `examples/` / `apps/`）
- 相关组件与可复用代码
- 构建与验证命令

---

## 步骤 2：制定实现计划

执行 `piv-plan-implementation` skill 的工作流（Validation-First）：

- 产出计划文件 `.codebuddy/plans/<feature-name>.md`
- **记下功能名**（下一步要用）

若已有 PRD/SDD/切片清单，直接继承其决策，不重新讨论。

---

## 步骤 3：实现

执行 `piv-implement` skill 的工作流：

- 严格按计划逐步实现
- 每步完成立即验证，不攒到最后

---

## 步骤 4：验证

执行 `piv-validate` skill 的工作流：

- 编译 + 静态检查（`git diff --check`、`build-all.bat` 无新增警告；
  改了画布再加 `cd designer && npx tsc --noEmit && npx vite build`）
- 行为验证（按计划的验证方法）
- 边界/异常路径覆盖

验证失败则回到步骤 3 修复，直到全部通过。

---

## 步骤 5：提交前审查

执行 `piv-review-changes` skill 的工作流：

- 对全部改动做通用技术审查
- 按改动领域加载对应的审查 skills（**7 个**，映射表见 `global-rule.md` §7 / `sop` §4；
  本工程没有 MCU，没有 DMA/中断那一族）
- **第四步强制 `adversarial-review` 三角色对抗裁定**（挑刺带证据 → 辩护找反证 → 改进只修成立项），
  报告含三方裁定表与健康度（成立率 / 驳回率）
- 产出审查报告到 `.codebuddy/code-reviews/`

发现需要修复的问题 → 回到步骤 3/4，修复并重验。

---

## 步骤 6：提交

前置条件：验证门禁 + 审查门禁都过，且改动范围已用 `git status` 逐条枚举（不手写清单）。
然后执行 `git-commit-style` skill 的流程（本项目唯一提交规范）：

- `[类型][模块] 描述` 格式，按逻辑分批原子化提交
- 输出变更摘要 +（如有）.codebuddy/ 层改动说明

---

## 最终总结

全部步骤完成后输出：

### 功能开发完成

- **原始需求**：$ARGUMENTS
- **功能名**：<计划中的名称>
- **执行步骤**：
  1. ✅ 加载上下文
  2. ✅ 计划已创建（.codebuddy/plans/<name>.md）
  3. ✅ 实现完成并验证
  4. ✅ 审查通过（审查报告路径）
  5. ✅ 已提交（commit hash）

**产出物**：
- 计划：`.codebuddy/plans/<name>.md`
- 审查报告：`.codebuddy/code-reviews/<date>-<name>.md`
- 改动文件：<列表>
- 提交：<hash>

**后续步骤**：
- `piv-create-pr` 创建 PR/MR（如需要）
- 推送远端：`git push`
- 继续下一个功能/切片

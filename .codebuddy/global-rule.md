# 全局强制规则（CStackGUI）
所有代码生成、代码修改、代码评审必须遵守以下规则，默认严格生效：

> **适用范围（CStackGUI）**：本仓库是 **Win32 桌面 GUI 项目**（Electron 画布 + C 运行时 + MinGW gcc），
> 不是固件工程。**2026-09-27 清理**：原第 1~3 节的硬件 / 中断 / RTOS 规则（配合那 8 个固件审查技能）
> 已换成「平台硬性规则 / 安全规范 / 资源与生命周期」三节，对 `runtime/`、`designer/` 与业务 C 代码
> **同样适用**，不再有"只在某类技能被触发时才适用"的例外。
> 本工程真正的硬门禁是
> `build-all.bat` → `examples\gallery\gallery.exe --selftest` → `tools\run-tests.bat`
> （C 层单测：JSON / 文档 / 类型表 / 事件表 + cg_kit 冒烟） → `tools\check-format.bat`
> （改了 `.cgui` 契约或控件类型时；它顺带检查 bat 编码），以及 README 第三章列的项目铁律。
>
> **动过任何 `.bat` 之后必须跑**：`powershell -NoProfile -ExecutionPolicy Bypass -File tools\bat-utf8.ps1 -Mode fix`
> —— 仓库 bat 统一 **UTF-8 无 BOM + CRLF + 开头一段纯 ASCII 前导**（先切 65001 再 `cmd /c "%~f0" %*` 重入）。
> cmd 用"启动这个 cmd 进程时的控制台代码页"解码 bat，UTF-8 的中文会被按 2 字节/字解码、行定位错位，
> 注释后半句被当命令执行（双击满屏 `"... is not recognized"`）；带 BOM 会让首行直接报错；带中文的 bat 里
> 不能出现 `goto` / `call :label`（标签扫描会漂移）。`-Mode check` 已并入 `tools\check-format.bat`。

## 1. 平台硬性规则
> **本工程是 Win32/GDI+ 桌面工具包 + 画布，没有 MCU**（2026-09-27 清理：原来这里的"寄存器/时钟/GPIO/DMA/NVIC"规则
> 随 8 个固件审查技能一起删了，仅在"给板子写配套固件"时才有意义）。保留下来的通用项：
- 系统符号运行期取（**零新增链接依赖**是本工程的硬约束），接口签名必须与官方声明**逐参数一致**
- 平台行为以官方头文件/文档为准；不许把自己的 bug 当成"系统不支持"的结论写进文档

## 2. 安全规范
- 所有数组、缓冲区必须做边界判断
- 禁止裸指针直接运算
- 字节流按帧切（`cg_frame_*`），不靠"读一次 = 一帧"的假设

## 3. 资源与生命周期
- 句柄 / GDI 对象 / 窗口：创建即配对释放（`error_handling_check` 查资源泄漏）
- 栈分配禁止大数组，大缓冲区必须全局/静态或由调用方提供

## 4. 评审优先级（分级，命中即打回）

按 P0 → P3 顺序审；**高档命中即打回，不进入下一级的讨论**。理由：本工程最贵的错不是不优雅，
是死机、丢字节、界面错位；而"内存安全有问题却在讨论命名"是最常见的优先级倒挂。

| 级 | 类别 | 必查 |
|---|---|---|
| **P0** | 正确性与安全 | 缓冲区越界 / UAF / 空指针解引用 / 未初始化 / 整数溢出截断 / 竞态 / 句柄与 GDI 对象未配对释放 / 返回值未检查 |
| **P1** | 平台与跨端契约 | 切帧不按字节流（读一次 ≠ 一帧）/ 字节序与校验 / 线程边界（收字节线程碰控件）/ 高 DPI 坐标换算 / `.cgui` 字段与 C 结构不一致 / API 签名与官方声明逐参数一致 |
| **P2** | 健壮与性能 | 错误路径与降级 / 超时与重连 / 重复计算与内存浪费 / 大缓冲的分配位置 |
| **P3** | 风格 | 命名 / 注释 / 复杂度 / 格式化 —— **只在 P0~P2 全过后才谈** |

> 本工程**没有 MCU**：中断上下文、DMA 缓存一致性、栈深度、看门狗、实时性优先级反转
> **不在审查范围**，别凭空造这些检查项（那是固件模板的残留）。

## 5. 输出要求
所有问题必须标注：文件+行号+风险等级+问题原理+修复示例

## 5.1 输出压缩强制规则（Caveman 常驻，默认开启）
**每条回复默认 full 档压缩**，无需用户重复触发。规则内核：
- 删：冠词、填充词（其实/基本上/一般来说/我们可以看到）、客套、对冲措辞、多余连接词。允许句子片段、短同义词。
- 保留一字不改：代码、命令、错误信息/日志、文件路径、控件/字段名、版本号、日期、URL。
- 准确性 > 压缩率：安全/资源释放/时序/协议等关键结论必须清楚，宁可多留词也不造成歧义。
- 例外：审查报告/PRD/SDD 正文不压缩（保证完整表达），外围对话说明仍压缩。
- 关闭：用户说"关闭caveman"/"正常模式"/`off`；切档：`caveman ultra`/`caveman wenyan` 等。
- 每轮持续生效，不因对话变长而回退。详见 `skills/caveman/SKILL.md`。

## 5.2 代码生成量压缩强制规则（Ponytail 常驻，默认 full 档）
**每次写码前默认走"决策梯子"**，能不写就不写、能复用就不重写。核心：最好的代码是从未写过的代码。
- **梯子**（按序检查，停在第一满足层）：需要存在?→已有?→标准库?→平台特性?→现有依赖?→一行搞定?→最小代码。
- **红线不砍**：缓冲区边界/资源释放/错误码/时序/协议一致性（切帧、字节序、校验）属"必要代码"，梯子跳过这些。
- **本工程禁 ultra**：过度压缩易漏防御（缓冲区、资源释放），锁 full 上限，用户坚持 ultra 才放开且逐条复核红线。
- **先读后省**：懒于方案，绝不懒于阅读——必须先读相关代码、追踪流程，再上梯子。
- 关闭：用户说"关闭ponytail"/`ponytail off`；切档：`ponytail lite`（更温和）。
- 与 PIV 流程正交：只影响"写多少代码"决策，不改质量门禁。详见 `skills/ponytail/SKILL.md`。

## 5.3 非破坏性文件操作强制规则（不删为先，默认开启）
**能覆盖就不删、能不建就不建**：删除类操作会触发风控与人工批准，零散删除等于把用户按在十几个弹窗前。
- **替代优先**：改内容用覆盖写（`replace_in_file`/`write_to_file`），不"先删再建"；清空文件用写空内容；
  重新编译**不要删** `build\obj`/`build\lib`（脚本自比时间戳，重编会覆盖 `.o`、`ar rcs` 覆盖归档）；
  重建输出目录直接往里写；被 git 跟踪的文件要"还原"用 `git restore` 而不是删除；
  临时探针/截图/提交信息文本一律落 `build\`（gitignore），**收尾不清理**。
- **硬红线**：禁 `rmdir /s /q`、`del /s /q`、`Remove-Item -Recurse`、`git clean -fd(x)`、通配符批量删除；
  禁删 `.codebuddy\`、`runtime\`、`designer\src\`、`docs\`、`examples\`/`apps\` 里的手写文件；
  禁删工作区之外的路径与用户数据目录。
- **确实要删**：合并成**一次**操作（完整路径、无通配符），先给「删除清单 + 原因 + 为何无法替代」，
  整个任务只请求一次批准；同一轮里连续第三次动删除命令就要停下来合并。
- 关闭：用户说"可以随便删"/`safe-file-ops off`。详见 `skills/safe-file-ops/SKILL.md`。

## 5.4 对抗性思维强制规则（`adversarial-thinking` 常驻，默认开启且**不可关闭**）

**凡准备输出"以下是 N 条问题 / 建议 / 结论"之前，先攻击自己的结论。**
AI 最常见的失败不是"不知道"，而是**自信地说错**；攻击的成本远低于错误修复的成本。

- **验证先于断言**：说"这里有 bug"之前先 grep / 读码证明它**真的会发生**（调用点齐全？开关开着？
  路径没搬家？exe 没被锁？命令**真的能失败**吗？）
- **允许否掉自己**：列出 N 条建议后逐条问"这条真的是问题吗"，**被否掉的也要写出来**（这是最有价值的部分）
- **区分"修"与"观测"**：修 = 改行为，需要语义判据；观测 = 加可见性，永远安全。
  跨越语义决策（产品 / 协议 / 观感）的改动**先只做观测**
- **对"不修"写理由**：防止后人误以为是 bug 而乱改，或误以为是设计而忽略
- **禁止反模式**：把自己刚列的建议当标准答案直接执行；用"能编译 / 门禁绿"代替"逻辑正确"；
  用数量代替后果；为了显得彻底而扩大改动范围

**四道闸门**（详见 `sop` §2.9）：出计划后（验证方法能失败吗）· 判门禁时（读日志不看回显）·
出审查报告时（每条 issue 都要自证）· 任何"N 条…"输出前（先否一遍自己）。
输出必须含：**确定项 / 已否掉的项 / 降级项 / 未验证假设**。

## 6. PIV 开发工作流强制规则（v0.1）

### 统一入口：`expert-teams` 选人，`sop` 定流程

任何开发类请求（新功能 / 改 bug / 改画布 / 改技能 / 并行 / 提交前）**先选团**：
`expert-teams` 按八团编制回答"这轮叫哪个团、最小加载集是什么、交接物是什么"；
再进 `sop` 拿流程：按请求类型路由（问答题不必走全流程）、串起 P0~P6 七段流水线、
给出**唯一权威的门禁命令表**（`sop` §3）与审查路由表（`sop` §4）。本节下表是"每段该调谁"的映射。
另有三条学自 Spec Kit 的**独立入口**（不是必走阶段）：**修 bug** 走"诊断 / 修复 / 验证"三段分离
（诊断的执行体 = `systematic-debugging`：没有根因调查不许提修复；修复前先由 `test-driven-development`
写一条会红的复现测试；没有验证的修复不算修复），**想法评估**走 intake → research → decide（go / needs-clarification / kill），
**建功能**才走下面的 P0~P7（含 P7 收敛）。
**命令写法以 `sop` §3 为准** —— 别处出现不同形态（缺 `cd designer`、写成 `build-all` 不带扩展名等）一律以该表纠正。

### 工作流自动触发机制
项目采用 **PIV 双循环框架**（参考 coleam00/skills），AI 必须根据用户意图和当前阶段自动进入相应工作流：

#### 外层循环（大需求）
| 触发条件 | 自动调用 Skill | 产出 |
|---------|---------------|------|
| 新功能需求但验收标准不明确、跨模块/硬件/协议 | `plan-create-prd` | `docs/PRD_*.md` |
| 需要架构设计、模块划分、新模块/重构 | `plan-architecture` | `docs/SDD_*.md` |
| 需求太大、无法一次完成、需要拆分任务 | `piv-slice-epic` | `docs/SLICES_*.md` |

#### 内层循环（每次开发必走，强制执行）
| 阶段 | 强制调用 Skill | 触发时机 | 产出 |
|------|---------------|---------|------|
| 0. 上下文 | `prime-codebase` | 会话开始且有开发任务 / 即将实现前 | 上下文总结 |
| 1. 计划 | `piv-plan-implementation` | 开发任务明确但无计划 / 实现前强制触发 | `.codebuddy/plans/*.md` |
| 2. 实现 | `piv-implement` + `test-driven-development`（写行为代码前） | 计划确认后 | 代码改动 + 先失败过的测试 |
| 3. 验证 | `piv-validate` | 实现完成后**强制触发**（进入审查前门禁） | 验证结果清单 |
| 4. 审查 | `piv-review-changes` | 验证通过后**强制触发**（提交前门禁）；第四步强制 `adversarial-review` 三角色对抗裁定 | `.codebuddy/code-reviews/*.md` |
| 5. 提交 | `git-commit-style` | 审查通过后 | git commit |
| 6. PR | `piv-create-pr` | 提交完成、用户要求创建 PR 时 | PR/MR |

#### 快捷全流程
| 触发条件 | 自动调用 Skill | 说明 |
|---------|---------------|------|
| 用户提出明确的、小范围功能需求（如"实现XX功能"） | `piv-run-full-loop` | 自动走完整个内层循环（0-5步） |

### 强制门禁点
以下环节为**质量门禁**，必须通过才能进入下一阶段：

1. **验证门禁**（`piv-validate`）：
   - 编译无新增错误/警告（`build-all.bat`；改了画布叠 `cd designer && npx tsc --noEmit && npx vite build`）
   - 行为验证通过（按计划的验证方法；GUI / 通信类改动走 `serial_verify` 真机实测）
   - 边界/异常路径覆盖
   - **每条验收命令都必须"能失败"**：判定要读日志，不信 `%errorlevel%` 回显
     （cmd 在解析整行时就展开了它，打印的是上一条命令的退出码 —— 实测踩过，见 `piv-validate`）

2. **审查门禁**（`piv-review-changes`）：
   - 按改动领域自动调用 审查 skills（映射表见下节；本工程适用的是 A 类 7 个）
   - 第四步强制 `adversarial-review` 三角色对抗裁定：无证据不指控、无反证不裁定；
     每条裁定成立的 critical/high 必须配**能变红**的回归判据，否则视为未处置
   - 无 critical/high 级别问题，或已修复
   - 产出审查报告到 `.codebuddy/code-reviews/`（含三方裁定表与健康度）

3. **计划门禁**（`piv-plan-implementation`）：
   - 任何实现前必须先有计划
   - 计划必须包含 Validation-First 的验证方法

## 7. 审查 Skills 自动触发规则（v0.1）

当 AI 生成、修改代码或执行 `piv-review-changes` 时，必须按改动领域自动调用：

### 审查 Skills 映射表

> **本工程是 Win32/GDI+ 桌面工具包 + 画布（`.cgui`），没有 MCU**。2026-09-27 清理后，下表只保留本工程
> 真会命中的领域：缓冲区、内存、通信协议（`cg_serial_*` / `cg_net_*` 是本工程的核心能力）、错误处理、
> 结构体、C 代码规范，以及画布与 `.cgui` 的界面观感（`design-taste`）。原先那 8 行针对 MCU 的
> （DMA / 中断 / Flash / 外设 / 低功耗 / RTOS / 看门狗 / 栈用量）随对应技能一起删除，只在"给板子写配套固件"
> 时才需要。技能分类总览与维护清单的权威定义见 **`.codebuddy/skills/INDEX.md`**。

| 改动领域 | 强制调用 Skill | 检查重点 |
|---------|---------------|---------|
| 缓冲区/字符串/memcpy | `buffer_overflow_check` | 边界检查、危险函数 |
| 动态内存/堆 | `memory_leak_check` | 泄漏、碎片、野指针 |
| 通信协议（串口/TCP/UDP/帧协议） | `communication_protocol_check` | 超时、校验、重传、切帧 |

| 代码规范 | `firmware_code_style` | 命名、注释、分层 |
| 界面观感/配色/字体/间距/动效/界面文案（画布或 `.cgui` App） | `design-taste` | 设计读盘+三旋钮、AI 味黑名单、质量地板（对比度/间距节奏/四态齐全）、文案一致性 |

### 触发规则
1. **写代码时主动审查**：生成代码后，立即按领域调用相关 skills
2. **piv-review-changes 环节**：全面调用所有相关 skills，产出审查报告
3. **问题修复后重验**：修复问题后重新运行对应 skill 验证
4. **AI 生成代码专项**：见下节，**每次 AI 改动都查**，不占"领域"槽位

### AI 生成代码专项（每轮必查）

本工程的代码几乎全部由 AI 生成，下列四类错误**编得过、跑得动、但语义是错的**，
编译器与门禁都拦不住，只有读头文件 / 实现才能发现：

| # | 幻觉类型 | 本工程的具体形态 | 怎么查 |
|---|---|---|---|
| 1 | **API 与签名** | `cg_*` / `cg_win_*` 少传或多传一个参数、参数顺序颠倒、返回值语义记反（如 `cg_frame_take` 返回帧长还是 0/1） | 打开 `runtime/include/cstackgui.h` 逐参数对照，不看记忆 |
| 2 | **常量与枚举** | 凭记忆写 `WM_*` / `CG_*` / `CG_FRAME_*` 的值；编造不存在的样式位 | grep 头文件确认存在且值正确 |
| 3 | **同名不同义** | 复制粘贴来的函数/变量名来自另一处上下文（同名但语义不同） | 回看被复制的那处实现，确认语义一致 |
| 4 | **注释与实现不符** | 注释写"失败返回 -1"，实现返回 0；注释写"单位 ms"，实现是 tick | 读实现，不读注释 |

> 判据：**"这个函数签名我是从哪里看到的？"** 答不出"刚读过头文件"，就是编的。

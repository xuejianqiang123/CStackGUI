# 审查报告：envsnap 清单改 INI 驱动 + 增删改查

日期：2026-10-08　范围：`git diff HEAD`（examples/envsnap 三件 + exe + 两处文档同步 + .gitignore 一行）
路由：`buffer_overflow_check`（解析/拼装全是字符串操作）+ `firmware_code_style` 口径（Doxygen/命名/分层/无 malloc）。

## 三角色审查

### R1 挑刺（20 项候选，摘关键）
1. ini_parse 行缓冲 512，超长行被切 → 可能产生截断脏行。
2. 分组表满（32）时 `cur` 未清空 → 名下键成"孤儿行"（不显示、保存丢失，与日志口径矛盾）。
3. `icontains` 指针推进读越界风险。
4. 删除分组时 `label[48]` 装 96 字节 data 的截断风险。
5. ini_save 借用 s_snap（96KB）会不会被 256 行清单撑爆。
6. 自检路径是否真的零盘副作用。
7. cg_free 配对（cg_file_read / cg_env / cg_app_dir / cg_path_join）。
8. 文档改动是否破坏 check-format 的文档口径门禁。

### R2 辩护（反证）
1. 脏行还会被 name[64] 再截断，只多显示一行、不越界；清单文件是用户手编的，512B/行的合理上限 → **降级为观测**。
2. 立住：孤儿行确实会静默丢失 → **必修**。
3. `a=='\0'` 先于比较返回 0，`i==nl` 判定在循环外 → 驳倒。
4. NK_GROUP 节点的 data 来自 s_groups（最长 47 字节，进表时已限长），48 装得下 → 驳倒。
5. 256 行 × 最长约 212B ≈ 54KB < 96KB，且导出与存清单是两个互斥的同步回调 → 驳倒。
6. selftest 输出证实：五按钮全走"自检模式：跳过"，on_ready 无 INI 读写日志 → 驳倒。
7. 逐处核对全部配对 cg_free → 驳倒。
8. check-format 复跑 `[ok] 文档口径与现状一致：6 课、10 篇文章` → 驳倒。

### R3 只修立住的
- **修复#2**：`ini_parse` 中 `group_ensure` 失败即 `cur[0]='\0'`，组与名下键一致丢弃，日志改为"名下的组与变量被丢弃"。修复后重编（零警告）+ selftest OK + check-format 全过。

## 已否掉的项
- 1/3/4/5/6/7/8，理由见 R2。

## 降级为观测的项
- 超长行截断产生的脏行：根治要给 parse 加"行过长即拒"逻辑，对一份用户手编清单属于过度防御，先观测。
- `cg_message_box` 只有确定钮 → 删除无二次确认：根治要运行时提供 yes/no 模态框，本轮不动 runtime（README 已写明恢复方式：ini 是唯一事实源）。

## 未验证假设

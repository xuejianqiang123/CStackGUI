# kit 字节操作（精易 `字节集_` 那一族的取舍）

## 先回答那个架构问题：**不引入"字节缓冲类型"**

`字节集_` 一族 27 条（反转 / 取左右 / 找子集 / 替换 / 插入 / 删除 / 分割 / 合并 …）。
要不要为此在 C 侧造一个"字节缓冲类型"（`struct { 指针 + 长度 }` + 自己的分配/释放）？

**结论：不造。** 三条理由：

1. 本工程的房屋风格已经把这件事覆盖了：`(data, len, …, out, out_size)` 进、**返回写出的长度**，
   错误码 -1 / -2（见 `cg_hex_encode` / `cg_hex_decode` / `cg_base64_*` 一整族）。
   加一个新类型等于**多一套所有权模型**（谁分配、谁释放、失败时半成品怎么收），
   而它换来的只是"少写一个 out 参数"。
2. 那一族里最常用的两个 —— **字节 ↔ 十六进制文本** —— **早就存在**（`cg_hex_decode` /
   `cg_hex_encode`，连分隔符与大小写都考虑了）。当年挖 `编码_` 那族时就做过了。
3. 剩下的操作大多**不需要缓冲**：反转原地做、查找返回下标、读写整数直接落到调用方的帧缓冲里。

## 于是只补了缺的基元（7 个）

| 函数 | 对应精易 | 说明 |
| --- | --- | --- |
| `cg_bytes_reverse(data, len)` | 字节集_反转 | 原地；len ≤ 1 / NULL 不动 |
| `cg_bytes_slice(data, len, from, count, out, out_size)` | 取左边 / 取右边 / 取中间 | **count = -1 = 取到底**；count 超剩余按剩余算（"取右边"的语义）|
| `cg_bytes_find(data, len, needle, nlen, from)` | 字节集_寻找子集 | 返回下标；可从 from 接着找 |
| `cg_bytes_get_u16 / get_u32` | （C 里没有，工控必需）| 按字节序读；**u32 用 long long 返回** |
| `cg_bytes_put_u16 / put_u32` | 同上 | 按字节序写进帧；**越界什么都不写** |

两条边界语义是刻意定的、也写进了头文件与测试：
- **越界/参数非法一律"什么都不写 + 返回失败码"** —— 半个 u16 写进帧里比报错更难查；
- **`get_u32` 用 `long long`**：用 int 的话 `0xFFFFFFFF` 正好是 -1，与错误码撞车，
  调用方无法分辨"读到 0xFFFFFFFF"与"越界了"。（这是写测试前自查语义时发现的，
  差点就把这个坑发出去了。）

## 验证

`tests/unit/test_kit_bytes.c`，5 个套件。几个关键断言：
- 切片：`count=-1`、取左/取右/取中、count 超剩余按剩余、from 越界返回 -1 且**输出没被动过**（哨兵字节验证）；
- 查找：同一图案出现两次时 `from` 能接着往后找、重叠图案、空 needle 返回 -1；
- 字节序：**明确的字节图案对照**（`12 34` 按大端 = 0x1234、按小端 = 0x3412），不靠"读回来看看"；
- 越界写：用哨兵验证"一个字节都没动"；
- 综合：拼一帧 Modbus 读请求（地址 + 功能码 + `put_u16` 两次）→ 再 `find` / `get_u32` / `slice` / `reverse` 拆一遍。

真机/实测输出：105 套件 / 2651 断言 / 0 失败；`--memcheck` 105/105 套件零新增存活堆块。

## 已知缺口

- **没做**替换 / 插入 / 删除 / 分割 / 合并：在定长缓冲上加它们，要么多一套"会成长的缓冲"
  （正是上面否掉的类型），要么让调用方自己 `memmove`。前者与结论冲突，后者调用方一行就够。
- `字节集_` 里还有一些偏"脚本语言味道"的（如"到字节集/到文本"的自动转换）—— C 是强类型的，
  这类在 C 侧没有对应需求，不做。

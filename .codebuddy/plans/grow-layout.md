# 实现计划 + **逐字契约**：grow（余量分配）

> 本文件是这一轮四个域（运行时 / 画布 / 示例 / 文档）的**唯一契约**。
> **与落盘代码不一致就报回来，以代码为准**；不要照着自己理解改契约文件（那是我 own 的）。

## 0. 要解决的问题

窗口拉伸不重排。`WM_SIZE`（`runtime/src/win32/cg_win_main.c:315`）现在只做一件事：
把新的客户区尺寸写进 `app->window->ev_x/ev_y` 然后派发 `size` 事件 —— **不移动任何控件**。
布局全靠绝对坐标，只有 splitter（分隔条）能在局部硬撑。

后果很具体：`[日志区 | 分隔条 | 发送区]` 这类布局，用户把窗口拉高之后，上部不动、下部留白。

这一轮加**一个字段**解决它，**不做完整布局引擎**（绝对坐标仍是主体）。

## 1. `.cgui` 契约（画布与运行时必须逐字照这个来）

widget 节点新增**可选**字段：

| 字段 | 类型 | 默认 | 位置 |
|---|---|---|---|
| `grow` | 整数 `0..99` | `0`（不写） | 与 `rect` 同级的 widget 字段 |

语义一句话：**容器变大时，多出来的空间按权重分给同一容器里 `grow > 0` 的兄弟；
与它位置重叠的兄弟（同一行 / 同一列）原地不动，排在这一行 / 列之后的兄弟整体平移。**
（"位置重叠 = 同一条带"，几何算法见 §2。）

- `grow: 0` 与不写等价；**序列化时不写出 0**（与本项目其它"缺省不写"一致）。
- 容错（画布 parse 与运行时 parse 都照这个来）：走 JSON 数字解析 —— **小数四舍五入、
  `true` 当 1、数字字符串按数字读**（`"7"` → 7），随后**负数与大于 99 的归 0**；
  不报错、不中断加载。
  > 这条是按**落盘代码**改的：运行时的 `cj_int`（`cg_json.c`）就是这个口径，与 `rect`
  > 等其它整数字段共用同一套解析；画布侧 `parse.ts` 已对齐它。
  > 2026-09-27 由画布域队友逐行核出，原先契约写的"非整数一律当 0"与代码不符。
- **两个轴用同一个权重**（只有一个数，不区分 X / Y）：横向与竖向都按它吃。理由见 §4。
- 只有**同一父容器里**的兄弟参与竞争；面板（panel）里的子控件同理（各自成组）。
- 画布**不做** grow 的实时预览（那等于在画布里实现一遍布局引擎，会毁掉所见即所得）。
  属性面板给一个 0..99 的数值输入 + 一句说明即可。

## 2. 运行时几何算法（`cg_layout_apply`）—— 逐字按这个实现

```c
/* runtime/src/core/cg_internal.h（core 内部，不对外） */
typedef struct {
    int x, y, w, h;     /* 进来是基准坐标，出去是算好的坐标 */
    int grow;           /* 权重 0..99 */
} cg_layout_box_t;

/** 把"容器尺寸从 base 变到 now"的差值按 grow 分配到各 box。
 *  纯整数算术、不碰 Win32（所以能纯单测）。 */
void cg_layout_apply(cg_layout_box_t *boxes, int count,
                     int base_w, int base_h, int now_w, int now_h);
```

**两个轴独立处理**（先横后竖，互不影响）。单轴上按**带（band）**分配 —— 这是写单测时
才想清楚的一步，下面附反例。

**什么是一条带**：把该轴上的兄弟按位置排序，**位置区间互相重叠**的属于同一条带
（直观说就是"同一行 / 同一列"）；起点 ≥ 带尾的才是下一条带。

每一条带：

1. `band_weight` = 带内成员权重之和；`sum_left` = 未处理带的权重和；`given` = 已分配量。
2. `take = (delta - given) * band_weight / sum_left`；**最后一条带直接吃余数**（`delta - given`）
   —— 一个像素都不许丢。
3. **带内每个 `grow > 0` 的成员各自吃这一份**（它们在同一个行/列里，各自都要把这一带填满，
   不是互相竞争）；`grow == 0` 的成员尺寸不变。
4. 带内成员按**更早的带**累计的 `shift` 平移；这一带吃掉的量由**后面的带**整体让出。
5. 缩到比设计尺寸还小时压到 0（`take` 记为"实际吃到的量"），不出负数。

竖轴与横轴同构（用 `y`/`h`）。

**为什么必须按带分（旧说法的反例）**：旧规则是"该控件之后的兄弟整体平移"，那么
`[终端 | 工具栏]` 这种左右并排的布局，窗口一变高就会把右边的**工具栏推到下面去** ——
看着像傻了。按带分之后：同一行里的两块要么**都**变高（都设了 grow），要么另一块**原地不动**
（没设 grow），都不会被推走。

**关键性质：不做增量累加。** 每次 `WM_SIZE` 都从**基准**重算 ⇒ 来回拉伸不会漂移、
不会积累舍入误差（`tests/unit/test_layout.c` 把这条钉成了断言）。

另外两条**可直接验证的性质**（同样钉了断言；2026-09-27 由文档域在复算里发现并建议写进契约，
比"正好贴住前一块"准确）：

- **平移保持带间距**：一条带之后的兄弟都平移同一个累计量 ⇒ **带与带之间的距离不变**
  （原来留的缝保持原样）。
- **末带边界**：只有它**本来就贴着容器旧边界**时，才会正好落到新边界 ——
  因为不丢像素的是"Σ实际吃到的量 == 该轴变化量"，而不是"末块一定贴边"；
  本来留了缝的，缝也保持原样。

## 3. 谁调用、基准从哪来（运行时侧，我 own）

- **基准 rects**：控件创建时（就是 `.cgui` 里的设计坐标）。
- **基准容器尺寸**：窗口**第一次 `WM_SIZE` 时的客户区物理尺寸**。因为窗口是按 `.cgui` 的
  `app.w/h` 建的、且先于 `on_ready` 里可能的"恢复上次窗口尺寸"，所以第一次 `WM_SIZE`
  拿到的就是设计尺寸 —— 这样**不用去猜窗口边框和菜单栏占多少**。
- 每次 `WM_SIZE`：先按 `cg_layout_apply` 算 rect → `SetWindowPos` 应用 → **然后**才派发 `size` 事件
  （业务在回调里读到的已经是对的新尺寸）。
- 面板递归：面板自己 move/resize 之后，用它自己的（基准尺寸 → 新尺寸）跑一遍它的子控件。
- **splitter 拖动之后，把当前 rects 回写成新基准**（用户的拖动就是"新设计"），
  否则下一次 `WM_SIZE` 会把拖动结果丢掉。
- **DPI 变化后重新取基准**（`WM_DPICHANGED` 会整体缩放控件并触发 `WM_SIZE`，
  不重取基准的话，这次缩放会被当成"用户拉伸"而被 grow 控件再吃一遍）。
- 尺寸一律用**逻辑像素**算（与 `.cgui` 的坐标同一套单位）：`WM_SIZE` 的 lParam 是物理值，
  先按 `cg_win_main.c` 里现有那条公式换成逻辑，再和同样来自 `.cgui` 的设计尺寸一起算；
  `cgw_sync_widget()` 落到原生窗口时内部再按 DPI 缩放 —— 所以布局这一路完全不碰缩放数学。
  （原先这里写"物理像素"是**文本错误**，落盘一直是逻辑像素；2026-09-27 由示例域与文档域
  各报一次后更正。）

## 4. 明确不做（v1）

- 不加 `sizePolicy` / `anchor` / 两遍尺寸协商 —— 不做完整布局引擎。
- 不做"只在某个轴吃"的独立开关。**一个权重、两轴同吃**。三条实用规则（按带模型重写）：
  1. **竖向想让它变高**：给"该变高的那一块"写 `grow`（经验上就是日志 / 内容区，不是底部的
     细条）。若同一行里还有并排的兄弟也该跟着变高，给它们**都**写 `grow`（同一带里各自填满）。
  2. **左右分栏**：给"该吃宽度"的那一栏写 `grow`；另一栏不写 —— 它的**宽度不变**，
     若不与前者重叠（属于后面的带）会被整体平移，若重叠（同一条带）就原地不动。
  3. **同一条带里，给"边界已经是这一带最外沿"的那块最安全**（右 / 下边界 = 带尾）：
     带内成员各自就地变大、**不互相让位**，所以边界还在带内的那块会长到同带更靠外的兄弟身上。
     "坐标最大"只是它的一个特例 —— 横轴上只要有一个全宽兄弟（比如横贯整行的状态栏），
     整行就被并成一条带，那时**坐标不最大的全宽块同样安全**（`serialterm` 的日志区就是：
     x 不是最大，但右边界正好是带尾）。v1 **不做"带内互让"**，用这条规避 ——
     2026-09-27 由文档域用"直接链接 cg_layout.c 的最小程序"实测出精确边界后写进文档。
- 不做 `WM_GETMINMAXINFO` 的最小尺寸联动。
- 不对 `menu` / `statusbar` / `toolbar` 做特殊例外（它们的 rect 本来就特殊，建议用户别给它们 grow）。
- 画布不做实时预览。

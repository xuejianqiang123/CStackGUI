## 深色：实测口径（这是本片唯一"用户能看见"的部分）

落点只有两处 —— **窗口底色**与 `cg_win_behind_rgb()` 的兜底。后者是"背后是什么颜色"的唯一出口
（自绘控件清底、无底色控件的 `WM_CTLCOLOR` 都问它），换掉它就整片跟着变，不必逐个重画控件。

✅ 跟随：窗口与 group/box/card/shape 底色、**没写 fg 的 label**、**没写 fg/bg 的 edit**、
terminal（RichEdit 走 `EM_SETBKGNDCOLOR`）、**没写 fg 的自绘文字**（复选框/单选/开关的标签）、
`progressring` 的轨道、`chart` 的画布区与轴标签、其余自绘控件的**底色**。

❌ 不跟随：`listbox`/`table`/`tree`（Win11 实测，试过 uxtheme 未公开序号 135/133/104 也无效）、
系统经典控件（tabs / combo 下拉 / monthcal / datepicker / statusbar / toolbar）、
`slider` 底槽、`progress` 的槽、以及**所有自绘控件的填充色**（与按钮同口径）。

> 一句总结（进了用户文档）：**它让界面暗下来，但不是一套完整的深色皮肤。**

## 探针抓出来的四处（都是"想不出来、只能跑出来"的）

1. **写了 `cgw_theme_apply()` 却从没在启动时调用它** —— 第一次截图里 listbox/表格/树照样白底，
   我以为是 API 不灵；其实是漏了调用。改成在 `cgw_create_native` 末尾**逐控件**调，
   运行期动态建的控件也自动跟上。
2. **`SetPreferredAppMode` 必须早于控件创建**（进程级开关）—— 晚调实测无效。
3. **深底暗字**：`cg_skin.c` 里画在**透明底**上的文字在深色下是深色 ⇒ 变浅（真缺陷，修了）。
   同一行带出**反向判断**：画在 M3 浅紫填充上的按钮文字**不能**跟着变浅（填充仍是浅紫）。
   两处同一个常量、结论相反 —— 已写进注释。
4. **`SetWindowTheme` 要 `-luxtheme`**（探针实测 `undefined reference to __imp_SetWindowTheme`）⇒
   走 `LoadLibraryW + GetProcAddress`，**不动用户的链接命令**（与 `RtlGetVersion` 同一做法）。

  `SetWindowTheme` 确实要新库（假设成立）、而上一轮的 advapi32 假设是错的。两次都只花一条编译命令。

## 样式字段的取值口径（最终版，两边一致）

**七个字段一律：值取不到的就算"没写"**（不置掩码、不顶掉命名样式里的值）。
- `font`：`cj_str` 取不到就不置位
- `fg` / `bg`：`cj_color` 读不出（= `CG_COLOR_NONE`）就不置位 —— 语法里**没有**"强制无色"的写法，
  所以不需要表达"写了但没值"
- `size` / `radius`：哨兵 `-2147483647-1`；`bold`：哨兵 `-1`（`cj_int`/`cj_bool` 分不出解析失败，
  只能传一个不可能是合法值的哨兵再比对）
- 画布侧同口径（`intOk`/`boolOk` 认不出来返回 `undefined` = 丢键）

> 这一条是**跨域对齐**的产物：画布域逐字对齐运行时的取值函数时发现 font/fg/bg 两边结论不同，
> 与其引进一个 `null` 写法表达"写了但没值"（要扩语法、扩文档、扩解析），不如让运行时也按
> "取不到 = 没写" —— 行为更符合直觉，且 `align` 那个"唯一例外"随之消失。

## 中性灰部件（2026-09-27 收口）

`progress` / `progressring` / `slider` 的**槽与轨道**、`led` 的灭态灯点、`chart` 的边框·网格·
轴标签·图例 —— 这些"浅灰细部件"原先写死在**八处**（含"滑块槽与图表网格同值不同用途"这种
按值 grep 必漏的情况），现在收在 `cg_skin_neutral()` 一处。

**验证手段也在这里换了一次**：此前判深色观感靠"看截图"，这一天里我读错了三次
（把标题栏当窗口底、把 progressring 轨道当已跟随、把 slider 的灰底当白底）。
改成**读像素数值**（`build\probe_px.ps1`，深/浅两张图各断言"该出现的出现、不该出现的不许有"），
并且拿**修复前**的旧截图跑同一断言验证它**能 FAIL** —— 断言不会失败就等于没测。

**没做成的一条（已如实记入文档）**：`slider` 的**画布底**由原生 trackbar 自己画，
PREPAINT 填背后色 + `CDRF_SKIPDEFAULT` 两条路试过，**像素一个都没变** ⇒ 撤掉半成品，
要彻底解决只能像 `progress` 那样换成自绘窗口类。

## 已知缺口 / 待办（不粉饰）

- **`listbox`/`table`/`tree` 的深色在 Win10 1809–21H2 上到底行不行，没验过**（本机只有 Win11）；
  代码保留 + 注释写明"未验"，文档按"不跟随"写。
- ~~**样式引用失效是完全静默的**~~ ⇒ **已补**（脚本 `cg_doc_t.style_missing` 计数 + 解析收尾报一条 WARN +
  `--selftest` 计入失败，与动作"未登记"同一个口径）。实测：引用失效的探针文档日志出 WARN、自检
  `样式引用失效 2 个`、**exit 5**；引用都有效的 gallery 是 0 个、exit 0。
  画布侧仍在设计期标红，两端合起来才不漏。
- 深色只覆盖"默认色"：自绘填充色与系统经典控件仍是浅色 ⇒ 要**完整**深色皮肤 = 重画那批控件，另一量级的工程。
- **还有一处同类"写死的默认文字色"没定论**：`cg_win_ownerdraw.c:123` 的 `widget_fg_or(w, 0x1D1B20)`
  （通用自绘控件的文字）。控件自带填充时它是对的（深字画在浅填充上），落到**透明底**就不对；
  现有截图里那批控件都写了颜色，所以**没被踩到**，不猜着改 —— 将来若看到某个自绘控件在深色下
  出现深底暗字，先查这里。（2026-09-27 深色示例域报回三处同类问题，这是排查时顺带发现的第四处候选。）
- 示例的命名样式里写死了浅色 `fg`（如 `#1D1B20`）⇒ **深色下示例会是混合观感**。本轮刻意没给示例开
  `app.dark`（保持外观不变）；要一个"深色示例"得另配一套配色。
- `designer/electron/main.mjs` 的 `styles` 菜单项由画布域补（`App.tsx` 已在收 `menu:"styles"`）。

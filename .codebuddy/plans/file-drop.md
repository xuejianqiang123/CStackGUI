# 文件拖放（窗口级 `drop` 事件）

目标：把固件 / 日志从资源管理器拖到窗口上就拿到路径（调试工具的日常动作之一）。
零新增链接依赖（`shell32` 早就在链接表里）。

## 设计

- **用老的 `WM_DROPFILES`，不上 OLE 拖放**：文件拖放这个场景老接口更省且够用
  （OLE 那套要写 `IDropTarget`、注册、处理跨进程数据对象）。将来要支持"拖文本 / 拖图片进来"
  再上 OLE 也不迟 —— 这条写在 `cg_win_drop.c` 文件头。
- **路径的生命周期是刻意的**：后端取完路径填进 `app` 的清单 → 派发 `drop` → **回调返回后立刻清空**。
  业务不必自己管这块内存，代价是路径只在回调期间有效（文档里写明"要留着就在回调里拷走"）。
- **可测的那半放在 core**：清单的填 / 取 / 越界 / 换 / 清 / 副本语义都在 `cg_event.c`
  （`cg_app_drop_put` 内部、`cg_drop_count` / `cg_drop_file` 对外）；win32 那半只剩
  "把 HDROP 读成 UTF-8 字符串"这十几行标准调用，单测碰不到（测试不 include `cg_win_internal.h`，按分层规矩）。
- 事件用**追加**方式进枚举（放在末尾）：事件值是位下标，插在中间会动到前面所有事件的值；
  `k_ev_names[]` 用的是**指定下标初始化**，本来就防这一手。

## 验证

| 层 | 手段 | 结果 |
| --- | --- | --- |
| 清单 API | `tests/unit/test_drop.c`：填/取/越界/负数/NULL app/再填是换不是叠/取到的是副本/清空 | 全过；`--memcheck` 抓"回调后没清"这类漏 |
| 事件链路 | `build\dropprobe\`（`app.events.drop` 绑定 + 处理函数）跑 `--selftest` | `未登记 0 / 事件不支持 0` ⇒ 事件名、绑定解析、窗口支持表三者对齐 |
| **真机拖放** | 探针跑起来后**真的从资源管理器拖文件进去** | 日志：`文件拖入：1 个（第一个：…\lesson02_inputs.cgui）` 等 4 次，路径完全正确；探针自己的 `DROP: 1 个文件` 也打出来了 ⇒ 解码 + 派发 + API 三段都成立 |

## 已知缺口

- **跨进程伪造 HDROP 是死路**（句柄在目标进程无效），所以这一片的"自动化真机验证"到此为止：
  再往后只能真拖（本片已由人手拖验证过 ✓）。另试过 PowerShell 发 `WM_DROPFILES` 探接线，
  但 `FindWindowW` 在我的工具环境里找不到窗口（返回 0），那条路没走通、**没有采信它的任何结论**。
- 拖**文件夹**进来时拿到的是文件夹路径本身（不递归展开）—— `WM_DROPFILES` 本来的语义，未额外处理。
- 本片没进示例（gallery 布局已排满）；使用方式是"`.cgui` 里给 `app.events.drop` 绑一个回调 +
  回调里 `cg_drop_count` / `cg_drop_file`"，写在头文件、`CGUI-FORMAT` 第 3 节与画布「支持库」里。
- 顺带把"宽字符 -> UTF-8 堆串"提成 `cgw_utf8_from_wcs`（cg_win_util.c）。后端里另有三处
  "写进调用方缓冲"的私有版本，签名不同，**暂未合并** —— 要合得一次改三处调用点，留作单独一片。

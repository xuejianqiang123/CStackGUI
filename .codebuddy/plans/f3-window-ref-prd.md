# F3：「引用另一个 .cgui」——多文件组装

> 状态：**PRD 待确认**（2026-10-10）。这是从 F2（多窗体）里切出来的独立契约 epic：
> T1~T3 的全套多窗体已交付并销账，T4 的“非模态 / 对话框里的 tabs”也已落地，
> 只剩这一条（PRD §4 当年明确写为“另一个 epic”）。本轮只做**调研 + 方案取舍**，不动代码。

## 1. 为什么要它

- **复用**：同一个对话框（端口设置 / 关于 / 登录）或同一块控件组（页眉页脚、工具条）
  要在多个界面里出现。现在是复制粘贴——改一处、其它几处不动，久了必然分叉。
- **对标**：py880 的“窗体引用”是它的原创能力之一（见 `py880-absorption.md`）。
- **单文件发布不能被破坏**：本工程的卖点是“一个 exe 双击就跑”。任何方案都必须保住它。

## 2. 已核实的事实（调研结论，不是假设）

| 事实 | 位置 |
| --- | --- |
| 运行时取界面的顺序：**显式 `cgui_path` → exe 旁同名 `.cgui` → exe 内嵌 PE 资源** | `cg_app_desc_t.auto_locate_cgui`、codegen 生成的 main.c 注释 |
| `cg_app_desc_t` 只接受**一份**文档（`cgui_path` / `cgui_text`），没有“合并第二份”的入口 | `runtime/include/cstackgui.h` |
| 一份文档有 **4 张顶层表**：`app` / `widgets` / `styles{}` / `roles{}` / `actions{}` | `runtime/src/core/cg_doc.c` |
| 导出固定 **6 个文件**（含 `.cgui` 与 `.rc`），有门禁守着“清单逐字一致” | F2 的 A8 验收 |
| 画布打开的就是工程目录里那份 `.cgui`，**没有“源文件 / 产物”的区分** | designer 工程结构 |
| 缺失/失效引用的一贯口径：**不静默丢**（计数 + WARN，`--selftest` 判失败） | 样式名、动作 handler 的既有处理 |

### 2.1 一个决定形状的硬约束

> 运行时**优先读磁盘上的 `.cgui`**（文件赢过 PE 资源），而画布编辑的正是那份文件。

这直接否掉了“只在导出时展开”那条捷径：

- 若导出把**展开版**覆盖回工程目录 → 用户下次打开，引用关系已经没了（退化成复制粘贴）；
- 若保留 `include` 字段不展开 → 磁盘上那份带 `include`，运行时又不认识它 → 打不开。

**结论：运行时必须认识 `include`（加载期按目录展开），发布态由编译把展开后的完整 `.cgui`
编进 PE 资源。** 于是：开发态改片段文件**立刻生效**（不用重新编译），发布态**自包含**（一个 exe）。

## 3. 范围决策（请重点看这三条；括号里是我的推荐与理由）

### D1 契约形状：顶层 `include` 数组（**推荐**）

```json
{
  "cgui": 1,
  "include": [
    { "path": "../common/port_dlg.cgui", "pick": "dlg_port" },
    { "path": "../common/footer.cgui" }
  ],
  "app": { ... },
  "widgets": [ ... 本文件自己的控件 ... ]
}
```

- **`include` 是数组、按顺序展开**：后面的盖前面的（与 `widgets` 的层叠顺序同一口径）。
- **`pick` 可选**：只取被引用文件里的**某个顶层节点**（按 id）；不写 = 取它全部顶层控件。
  有了 `pick`，一个 `.cgui` 里可以放好几个可复用片段，不必为每块都开一个文件。
- **被引用文件的 `app` 节点一律忽略**：窗口属性只有一个，属于主文档。
- **被引用的 `styles{}` / `roles{}` / `actions{}` 合并进来**（见 D2）。
- 老文件没有这个字段 ⇒ **零行为变化**（与 `center` / `roles` 那两次同一口径）。

**不做**顶层 `windows[]` 数组（F2 的 D2 当年就否掉了，理由仍然成立：会分裂文档模型）。

### D2 冲突策略：分两类，**都不静默**（**推荐**）

| 冲突 | 策略 | 为什么 |
| --- | --- | --- |
| **控件 id** | **报错**（画布红 + `--selftest` 红，不做自动改名） | id 是事件绑定与 `cg_find` 的钥匙；静默改名 = 回调查不到、控件找不到，正是本项目“不许静默丢”要防的事 |
| `styles{}` / `roles{}` / `actions{}` 同名 | **主文档优先 + 一条 WARN**（不报错） | 与既有“重名后者覆盖 / 失效引用计 WARN”的宽容口径一致；样式同名很少是真错误，报错太吵 |

### D3 画布里被引用的子树：**只读**（**推荐**）

- 被引用的控件在画布上**照常渲染、能选中看属性**，但**不能改**（改了会被下次加载覆盖，
  还会在保存时造成“写回哪一个文件”的歧义）。要改就打开源文件改。
- 只读的呈现：层树里该节点带一个“引用”标记，属性面板顶部一句“来自 xxx，改它请打开源文件”。
- **不做**跨文件回写（把改动写回被引用的文件）：那会让一次保存同时改多个文件，
  撤销栈、脏标记、失败回滚全都要跟着劈开，代价与收益不成比例。

## 4. 非目标（明确不做）

- 运行时**动态**换界面（运行时加载全新的 .cgui 重建窗口）。
- 被引用文件里再引用时**跨文件双向同步**（见 D3）。
- 片段的“参数化”（引用时改里面的文字/坐标）——那是模板系统，另一个量级。
- 画布同时打开多个工程做“多工程”管理。

## 7. 风险（先写下来，别到时当成意外）

1. **路径基准**：运行时从 PE 资源加载时“没有目录”。缓解：资源里存的就是展开版，
   只有从文件加载（开发态）才会去解析 `include`（那时一定有目录）。
2. **回调注册**：引用来的控件带的 `events` 名字，必须在宿主工程的 `CG_BIND` 表里，
   否则 `--selftest` 会报“未登记”——这是**期望行为**（与任何共享片段一样），但要在文档里说清：
   引用一段界面，**也要**把它的回调一起带上。
3. **画布保存的往返**：保存时必须把引用来的子树摘掉、只留 `include`，否则下次打开会重复一份。
   这是 P4 最容易出错的一步，要用往返探针（A2）盯住。
4. **门禁面**：`check-format` 跑 5 个示例的往返；新增字段要跟着补探针，否则“丢了不报错”。

## 8. 已拍板（2026-10-10；逐条给“为什么”，随时可以推翻）

| 决策 | 拍板 | 为什么 |
| --- | --- | --- |
| D1 的 `pick` | **要** | 没有它就得引入“片段文件”这**第二种文件语义**（一个文件 = 一段，且它不是可运行界面）。有了 `pick`，任何现有 `.cgui` 都能当来源、只取其中一块 —— 成本几乎为零（按 id 挑顶层节点），却省掉一整套新概念 |
| D3 只读 vs 回写 | **只读 + 一键跳到源文件** | 回写意味着“一次保存改多个文件”：撤销栈、脏标记、失败回滚、并发（另一个画布实例也开着它）、只读文件权限全都要处理，代价远大于便利。只读的痛点只有“想改片段要另开文件”，用**引用节点一键打开源文件**（画布本来就能打开文件）几乎零成本地消解掉 |
| 优先级 | **P1 的两端 + P2 同轮；P3/P4/P5/P6 随后** | 不是“先 P1+P2”就完事：画布若不认识 `include`，手写的文件用画布一保存就**静默丢失**（违反本项目铁律）。所以**画布保真与运行时展开必须同轮**，UI（插入引用 / 只读标记 / 跳转）可以最后 |

补充两条执行口径：

- **id 冲突**：报错，且错误信息要**带来源**（哪个 id、来自哪个文件）——自动改名等于“静默丢”，不做。
- **P1 的实施顺序**：先画布侧保真（`parse` 保留 + `serialize` 写回 + 往返门禁），再运行时侧展开
  （此时还没有任何生产者，保真先落不会破坏任何东西；运行时展开一到位，功能即生效）。

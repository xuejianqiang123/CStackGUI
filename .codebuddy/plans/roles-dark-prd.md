## 1. 需求与场景

1. **深色下一半控件破相**：用户选了 `app.dark`，按钮还是浅紫、输入框还是白底——界面像两个时代拼的。
   今天唯一的自救是给每个控件手写深色值，浅色下又破——**没有一套值能同时伺候两个模式**。
2. **语义色改一处全变**：品牌色/警示色散在几十个控件上（styles{} 缓解了字号复用，但**颜色没有语义**，
   "把警示红换掉"仍要逐个找）。roles{} = 一处定义、按名引用。
3. **深浅两份值**：styles{} 的值是单份的，没有"深色下用另一个值"的槽位。

## 2. 范围决策（推荐已给，说"继续"按推荐进 SDD）

### D1 劈成两刀，先 G2 后 G1（**推荐**）
- **G2 内置皮肤深色化**（纯运行时，**零契约变更**）：把 `cg_skin_neutral` 收拢成规矩，补齐按钮/勾选/
  开关/进度/圆环/**edit 底色**的深色变体。这是"完整深色皮肤"的大头视觉收益，且不碰契约、不碰画布。
- **G1 色彩角色系统**（契约 + 运行时 + 画布）：`roles{}` 顶层表 + `@角色名` 引用 + 深浅求值。
  G2 先行因为它解决"内置控件破相"（最大视觉缺口）且零风险；G1 解决"用户写死的颜色深浅联动"。
- 反方案（一锅端）否掉：G1 的契约设计会被 G2 的实现细节拖住，两件事的验收也搅在一起。

### D2（G1 契约形状）顶层 `roles{}` 表，引用 = 色值位置的 `"@名字"`（**推荐**）
- 形状仿 `styles{}`：`"roles": { "accent": { "light": "#6750A4", "dark": "#D0BCFF" } }`。
- 引用写在**现有颜色字段的位置**：`"fg": "@accent"`——不新增 `fgRole` 之类平行字段
  （那会让 style 字段面翻倍，且"三形态"合并规则要为每个新字段重讲一遍）。
- `@` 前缀有先例：菜单项文字的 `| @动作名` 就是"值位置上的引用"（textcodec）。
- 容错与 styles{} 同口径：`@` 指向不存在的角色 = 当没写（不报错）；角色值非法 = 该字段跳过。
- **alpha 口径**：角色值接受 `#AARRGGBB`，但 GDI 消费端大多不透明——与现有 fg/bg 完全同口径，
  角色不做例外（契约 2.2 已有"值取不到算没写"的地，不新增语义）。

### D3（G1 求值时机）解析时**挂引用**，theme 钩子里**求值写回**（**推荐**）
- `style_mask` 新增 fg/bg 的"是角色引用"两位；`cgw_theme_apply`（已有换刷/清缓存/逐控件/重绘全流程）
  里先做一遍"角色 → 具体值"写回 `w->style.fg/bg`，消费端（皮肤全部读取点）**零改动**。
- 反方案（每控件绘制时现场解析）否掉：15+ 个读取点全要改成"先查角色"，扩散面大、每帧开销；
  挂引用 + 钩子求值把改动收在解析与 theme 两处。

## 4. 非目标（明确不做）

- **系统经典控件的全染色**：edit 白底能否入 dark hook、清单控件 Win11 深色失效、菜单配色——平台边界，
  G2 尽力（edit 走自绘底色的路），但不承诺"全部原生控件随主题"。
- chart 系列/terminal 行色的角色化（它们是功能语义色不是主题色；要做也是把它们挂到**内置**角色上，排 T4）。
- CSS 式继承/层叠/选择器——styles{} 已有的"这不是 CSS"边界原样适用。
- 画布的深色实时预览（§1.1 既有取舍不变；A7 的"按当前模式"指的是画布跟随 app.dark 的**静态**取值）。

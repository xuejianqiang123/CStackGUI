# 【CStackGUI 进阶】校验与摘要：让发出去的帧不被认错，拿到的固件能对上

> 本系列共 10 篇（导读 + 六课 + 实战 + 案例 + 本篇），本篇是第 10 篇。
>
> 这一篇不看界面 —— 讲一个调试工具离不开的底子：**CRC 让接收方知道帧有没有坏、哈希证明固件没被改过、
> 进制与补码把一个寄存器值看明白**。这些能力都在 `cstackgui.h` 里，业务代码照样只 include 它一个头。
>
> 本文没有截图：这里全是命令行与日志里的字符串。

## 一、为什么这三件事绕不开

写跟硬件打交道的工具，一定会遇到下面三种"对不上"：

1. **你发的帧，板子收到的可能已经不一样了** —— 线上一根毛刺就能翻一位。板子要能自己判断"这一帧坏没坏"，
   唯一的办法是你在帧尾挂一段校验，它收到后当场重算、比对。
2. **你手上的固件，和发布页上那份可能根本不是同一个** —— 文件名一样、大小一样，烧进去才发现不对。
   摘要（哈希）就是"是不是同一份"的证据。
3. **协议文档说"这个寄存器是 12 位有符号"，报文里给的是 `0xFFF6`** —— 它其实是 **-10**。
   把值在十六进制 / 二进制 / 十进制之间来回看，是嵌入式与工控的日常动作。

这三件事在 CStackGUI 里是**一套普通函数**：不建窗口、不碰控件，所以回调里、`on_ready` 里、
甚至一个纯控制台小程序里都能直接调。业务代码仍然只 `#include "cstackgui.h"`。

## 二、CRC：让接收方认帧

CRC 的入口是 `cg_crc16()`（CRC16/**Modbus**，工控帧最常用的那个）和 `cg_crc32()`
（IEEE 802.3 / zlib 同一套）。算一段内存，返回一个整数。

**拼一帧 Modbus RTU「读保持寄存器」**（从站 `01`、功能码 `03`、起始地址 `0x0000`、读 `10` 个寄存器）——
用 `cg_modbus_build_read()`，**字节顺序、CRC、帧长都由框架摆好**：

```c
unsigned char frame[8];
int           n = cg_modbus_build_read(CG_MODBUS_RTU, 0, 0x01, 0x03, 0x0000, 10,
                                       frame, sizeof frame);
/* n = 8，frame = 01 03 00 00 00 0A C5 CD */

if (cg_crc16(frame, n) != 0) {                      /* 现场自校验：含 CRC 的整帧再算一遍必须是 0 */
    cg_log(CG_LOG_ERROR, "帧 CRC 自检没过，别发出去");
    return;
}
cg_serial_t *ser = cg_widget_serial(cg_find(app, "ser_main"));
if (ser) cg_serial_write(ser, frame, n);            /* 同步写；< 0 表示失败 */
```

收到回应之后**别自己剥 `0x80`**（异常响应的功能码在线上是 `原功能码 | 0x80`，这是最容易漏的一步），
交给 `cg_modbus_parse()`：

```c
cg_modbus_rsp_t r;
int ret = cg_modbus_parse(CG_MODBUS_RTU, buf, n2, &r);

if (ret == -2) {
    cg_log(CG_LOG_ERROR, "帧 CRC 不对 —— 线上的数据坏了，不是协议不对");
} else if (ret != 0) {
    cg_log(CG_LOG_ERROR, "响应帧格式不对（%d）", ret);
} else if (r.exception) {
    cg_log(CG_LOG_ERROR, "从站报异常码 %d", r.exception);   /* 1 非法功能 / 2 非法地址 / 3 非法数据 / 4 从站故障 */
} else {
    for (int i = 0; i < r.nvalues; i++)
        cg_log(CG_LOG_INFO, "寄存器 %d = %u", i, r.values[i]);
}
```

TCP 一样用，只是第一个参数换 `CG_MODBUS_TCP`、再给个事务号：`cg_modbus_build_read(CG_MODBUS_TCP, tid, ...)`
（带 7 字节 MBAP 头、**没有** CRC）；`cg_modbus_parse(CG_MODBUS_TCP, ...)` 同样认。

三条要记住的现场经验：

- **帧结构**（想自己拼的时候用）：`[从站][功能码][地址高][地址低][数量高][数量低][CRC 低][CRC 高]`。
  CRC **低字节在前**，摆反了板子一定回错误帧 —— `cg_modbus_build_read()` 摆的就是这个顺序，
  你也可以用 `cg_crc16()` 自己摆（它返回的是一个 16 位整数，**字节顺序要你自己摆**）。
- **"含 CRC 的整帧再算一遍 = 0"** 是这类协议最好用的自校验习惯：拼完帧先自己算一次，
  结果不是 `0` 就说明前面哪一步错了，**别发出去**（这也是很多串口工具"回环自测"时检查的第一件事）。
- **空输入返回 `0xFFFF`**：`cg_crc16(NULL, 0)` 得到的是 Modbus 的初值 `0xFFFF`，这是定义、不是 bug。

整段文件也可以用 CRC 核（比如出厂前对镜像算一个值贴上去）：

```c
static void log_file_crc(const char *path)
{
    unsigned crc;
    if (cg_crc32_file(path, &crc))                       /* 分块读，不把整个文件塞进内存 */
        cg_log(CG_LOG_INFO, "%s CRC32 = %08X", path, crc);
    else
        cg_log(CG_LOG_ERROR, "%s 打不开或读出错，CRC 不算了", path);
}
```

`cg_crc32()` 的参考值：文本 `"123456789"` 的 CRC32 是 `0xCBF43926`（和 zlib 一致），
`cg_crc16()` 的同一个文本是 `0x4B37`。拿这两组值对一下，就知道自己的实现没跑偏。

## 三、哈希：让别人能核对文件

CRC 管"路上有没有坏"，**哈希（摘要）管"是不是同一份"**。它们是两回事，别混用。

`cg_hash()` 对一段内存、`cg_hash_file()` 对一个文件算摘要，算法名从
`"md5"` / `"sha1"` / `"sha256"` / `"sha512"` 里选（大小写不敏感），**返回的是小写十六进制的堆串**：

```c
static void check_firmware(const char *path, const char *expect_md5)
{
    char *md5 = cg_hash_file(path, "md5");              /* 分块读，几十上百 MB 的镜像也不占内存 */
    if (!md5) {                                         /* 算法名不认识 / 文件打不开 / 内存不足 */
        cg_log(CG_LOG_ERROR, "打不开 %s，摘要算不出来", path);
        return;
    }

    if (cg_str_equal(md5, expect_md5))                  /* 忽略大小写比较 */
        cg_log(CG_LOG_INFO, "%s 摘要一致，就是这份固件", path);
    else
        cg_log(CG_LOG_WARN, "%s 摘要不符：期望 %s，实得 %s", path, expect_md5, md5);

    cg_free(md5);                                       /* 返回的是堆串，用完必须 cg_free */
}
```

发布固件时把 MD5/SHA-256 一起贴出来，用户手上算一遍、对一下，就能确认没下错、没传坏。
对一段内存（比如刚收完的一整个文件内容）算摘要，用 `cg_hash(buf, len, "sha256")` 即可。

**两者的分工**：

| | CRC（`cg_crc16` / `cg_crc32`） | 哈希（`cg_hash` / `cg_hash_file`） |
| --- | --- | --- |
| 干什么 | 让**接收方**当场知道这一帧在路上有没有坏 | 让**任何人**事后核对数据/文件没被改过 |
| 强度 | 检错用：能发现传输里常见的位翻转、丢字节 | 摘要用：改一个 bit 摘要就全变，想伪造得连摘要一起重算 |
| 长度 | 16 位（Modbus）/ 32 位 | 128 / 160 / 256 / 512 位 |
| 放在哪 | **挂在帧尾，跟着帧一起发** | **单独记下来**（版本信息、日志、发布页），事后对 |
| 典型场合 | 串口 / 网口的每一帧 | 固件镜像、发布包 |

> 一句话：**CRC 是"这帧有没有坏"，哈希是"这是不是同一份"。** 别拿 CRC32 当防篡改的摘要用。

## 四、进制与补码：把一个寄存器值看明白

### 4.1 十六进制 / 二进制 / 十进制来回看

`cg_int_to_base()` 把整数按任意进制（2..36）写成文本，**输出一律大写**（跟数据手册、寄存器表的写法一致）；
`cg_base_to_int()` 反过来，认 `0x` / `0b` / `0o` 前缀（调试工具里到处是这种写法），但**整串必须合法**；
`cg_base_convert()` 是"字符串进、字符串出"的直接互转：

```c
static void show_register(const char *label, unsigned long long raw, int bits)
{
    char      hex[32], bin[80], dec[32];
    long long v = cg_to_signed(raw, bits);              /* 低 bits 位按补码解释成有符号数 */

    cg_int_to_base((long long)raw, 16, hex, sizeof hex);   /* 大写十六进制 */
    cg_int_to_base((long long)raw,  2, bin, sizeof bin);   /* 二进制：看位段最直观 */
    cg_int_to_base(v,              10, dec, sizeof dec);   /* 十进制：负数带前导 '-' */
    cg_log(CG_LOG_INFO, "%s: 0x%s  %s  %s", label, hex, bin, dec);
}

/* show_register("温度", 0xFFF6, 12) 打印：
   温度: 0xFFF6  1111111111110110  -10            */
```

`cg_hex_encode()` / `cg_hex_decode()` 管的是"字节 ↔ 十六进制文本"（不涉及进制解释，就是字节的写法）：
编码时可以指定分隔串与大写；解码时**空格 / 制表 / 换行 / 逗号 / 连字符都当分隔符**，
`1A2B` 这种不写分隔的也认。收发日志里最常用的就是这一对：

```c
static void hex_roundtrip(const unsigned char *bytes, int n)
{
    char          text[128];
    unsigned char back[64];
    int           m;

    cg_hex_encode(bytes, n, " ", 1, text, sizeof text);   /* 大写，每字节间一个空格 */
    cg_log(CG_LOG_INFO, "HEX: %s", text);

    m = cg_hex_decode(text, back, sizeof back);           /* 大小写都认；分隔符可有可无 */
    if (m == n && memcmp(back, bytes, (size_t)n) == 0)
        cg_log(CG_LOG_INFO, "HEX 往返没跑偏");
}
```

### 4.2 补码：`0xFFF6` 按 12 位就是 -10

协议给"12 位有符号"时，报文里的 `0xFFF6` 不是 65526，而是 **-10**。它们就是干这个的：

```c
/* 读回：低 12 位按补码解释 */
long long         v   = cg_to_signed(0xFFF6, 12);       /* -10 */

/* 写出：把 -10 写成 12 位补码，才能塞进帧里（负数不能直接放进去） */
unsigned long long raw = cg_from_signed(-10, 12);       /* 0xFF6 */
```

- `bits` 取 **1..63**：给了 `64` 或越界，函数就按原样返回（**不做符号扩展**）—— 别拿它当"64 位无符号转有符号"用。
- 12 位只是最常见的例子；8 位（`int8`）、16 位（`int16`）同理，改 `bits` 就行。
- 把 `cg_to_signed()` 和 §4.1 的 `cg_int_to_base()` 串起来，就是"报文给十六进制、界面显示十进制"的标准动作。

## 五、几条边界，知道了就不会踩

1. **CRC 与哈希别混用**：CRC 给接收方当场验帧，哈希给所有人事后核对文件。拿 CRC32 当"防篡改"用是错的。
2. **Modbus 的 CRC 低字节在前**，字节顺序由你摆 —— 这是工控帧最常见的"明明算对了、板子却不认"。
3. **`cg_crc16()` 空输入返回 `0xFFFF`**（定义如此）；真正有用的是 **"含 CRC 的整帧再算一遍 = 0"**，
   拼完帧先自检一次再发。
4. **进制输出一律大写**；要小写十六进制用 `cg_hex_encode()`。`cg_base_to_int()` 要求**整串合法**、
   溢出算失败（`"1A 2B"` 是两段，中间有空白就失败，不会被拼成一段）。
5. **换行 / 空白不是问题**（`cg_hex_decode` 把一堆分隔符都当分隔），但**半个字节**（落单一个 hex 字符）算写错。
6. **`_file` 版本是分块读的**：几十上百 MB 的固件不会整个进内存；但它们是同步调用，
   别塞进每帧都跑的高频回调里。
7. **`cg_hash()` / `cg_hash_file()` 返回堆串，必须 `cg_free()`**；失败返回 `NULL`（不是空串），先判空再用。
8. **CRC 逐位算、不建表**：好处是天然线程安全、代码短，代价是比查表慢约 8 倍 ——
   协议帧和几 MB 的文件都够用，上百 MB 的大批量场合另说。

## 六、把它用起来

给现场留证据的两条习惯，比记函数签名更重要：

- **发帧前把 hex 与 CRC 写进日志**（`cg_log()`，或灌进 `terminal` 控件）：出问题时，
  "当时到底发了什么字节"是唯一能对账的东西。
- **固件摘要写进版本信息 / 日志**：烧之前算一遍、跟发布页对一遍，比烧完发现不对再返工便宜得多。

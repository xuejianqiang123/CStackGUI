# 计算器：上面输公式，下面出结果（深色科技感）

> 目录 `examples\calc\`　编译 `build-app.bat calc`　运行 `examples\calc\calc.exe`
> 自检 `calc.exe --selftest examples\calc\calc.cgui`
> → 控件 15 个 / 触发回调 6 次 /（未登记·事件不支持·绑定出错·动作出错·样式引用失效 全 0）→ `selftest OK`

窗口标题与界面文字是「计算器」；**工程目录用 ASCII 名 `calc`** —— 不是不喜欢中文，是编不动：
MinGW 的 `as.exe` 处理不了非 ASCII 的**绝对路径**（`Fatal error: can't create ...\计算器\lib\main.o`），
而构建脚本一律用绝对路径，所以中文目录名在这一版工具链上必然失败。

界面按手绘草图落地：**两块上下分组，铺满 700×500**。第一块「计算」上面输入公式、下面直接出结果；
第二块「长度计算」上面粘多行文本、下面给出字符数 / UTF-8 字节数 / 行数。深海军蓝底 `#070B14`
+ 青蓝强调色 `#22D3EE`，配色全在 `.cgui` 的 `styles{}` / `roles{}` 里。

## 一、它演示什么

- **输入即出结果**：公式框的 `change` 直接触发求值，不用点按钮、不用按回车；多敲一个字符结果就跟着变。
- **真正能写公式的求值器**：递归下降解析，支持 `+ - × ÷ * /`、`()` 括号、一元正负号、小数、
  百分号（`200×15%` = 30）、科学计数与千分位逗号；先乘除后加减。除数为 0 / 括号不配对 /
  认不出的字符 / 结果溢出都给中文原因，不静默算错。
- **错误提示有分寸**：预览时只提示"确实错了"的情况（除数为 0、非法字符），式子还没敲完
  （空公式、`12 +`、`(1+2`）就留白，不一直闪提示；点「计算」按钮则给出完整原因。
- **文本长度统计**：按 Unicode 码点算字符（中文 1 字符 / 3 字节）、按 UTF-8 算字节、按换行算行数，
  `\r\n` 只算一次，空文本 0 行。边打字边刷新，也能点按钮重算。
- **一个函数服务多个入口**：公式框的 `change` / `submit` 与按钮 `click` 都落在 `ca_compute`，
  文本区同理落在 `ca_len_show`，不存在两套算法对不上。

`.cgui` 里 6 个控件的 id 保留了设计器草图自动生成的 `edit_mw7q...` 原名（在 `main.c` 里用
`W_FORMULA` 等宏起可读别名），所以回到画布继续拖也不会跟逻辑脱节。

## 二、怎么用

```bat
rem 仓库根目录
build-app.bat calc
examples\calc\calc.exe
examples\calc\calc.exe --selftest   rem 不开窗自检：6 个事件全合成触发一遍
```

编译产物就落在工程目录里：**`examples\calc\calc.exe`**（约 590 KB，界面资源已嵌进 exe，
双击就能跑，不用传 `.cgui` 参数）。它原本和所有示例 exe 一起被 `.gitignore` 的
`examples/*/*.exe` 忽略，文件树和 `git status` 里都不显示，很容易被误认为"没编译出来"；
2026-11-08 起加了白名单 `!examples/calc/calc.exe` 单独放行，现在目录里能直接看到。
其余示例仍按项目约定不入库，需要 exe 时跑一次 `build-app.bat <工程名>` 即可。

| 输入 | 结果 | 说明 |
| --- | --- | --- |
| `12 + 7 × 3` | `33` | 先乘除后加减 |
| `(12+7)*3/2` | `28.5` | 括号 |
| `200×15%` | `30` | 数字后的 `%` = ÷100 |
| `1,000 + 2.5` | `1002.5` | 千分位逗号会被丢掉 |
| `1/0` | `除数不能为 0` | 硬错误，输入时就提示 |
| `(1+2` | 留白 → 点按钮显示 `括号没有配对` | 中间态不打扰 |

全角 `×` `÷` `−` `＋` `－` `（` `）` `％` 都会归一化成 ASCII 再算；其它非 ASCII 字符明确拒绝。
界面上「计算」按钮是**显式重算 + 看完整错误原因**的入口，实时预览是主路径。


## 四、踩过的坑（都是截图 / 探针实测出来的）

1. **输入框边框只画半圈 —— 已在公共运行时根本修复**：最初四个 `edit` 用 `"border": 6`
   时，实测只有「左边一小截 + 底边一条线」，上 / 右整段缺失，多行框右下角还有缺口。
   加临时诊断（`GetClipBox` / `GetPixel` 写日志）定位到：`GetWindowDC` 给子控件的可见区是
   `(0,0,w-1,h-1)`，最右一列 / 最下一行根本画不上去（那两列 `GetPixel` 直接返回
   `CLR_INVALID`）；而 `runtime/src/skin/cg_skin_edit.c` 的 `sk_edit_ring()` 用
   `RoundRect` + 画笔描边，GDI 的笔沿路径往右下铺，右 / 下两条路径正好压在这条不可绘制
   的边界上被裁掉。焦点环是 2px 笔，侥幸有一像素落进可见区，看着才"完整"，所以一直被
   误判成"只有非焦点框坏"。放开 DC 裁剪（`SelectClipRgn`）无效 —— 不是 `WM_NCPAINT`
   更新区域的问题。**修复**：`sk_edit_ring()` 改成「外圆角区域 − 内圆角区域 = 环形 HRGN，
   再 `FillRgn`」，填充是面而不是线，外边界直接取 `w-1` / `h-1`，整圈落在可见区内，
   与笔宽 / 裁剪边界再无关系；圆角半径按矩形尺寸夹取，`rad` 过大也不会退化。
   顺带加 `sk_edit_edge_tone()`：深色底把 M3 刺眼的浅灰环换成按底色自适应抬亮的冷蓝线。
   当时以为四个 `edit` 的 `"border": 6` 已经四边闭合 —— 其实只修掉了画笔描边那半圈，
   细线样式还有一轮「客户区覆盖」的漏网问题，见第 2 条。
2. **"边框还是只有半圈"的真因是环画进了客户区（上一轮"线太淡 / 缩放抹掉"是误判）**：
   第一版 `sk_edit_edge_tone()` 把深色线压成 `RGB(0x3D,0x5B,0x78)`，后来按底色自适应
   抬亮到 `#5C85BC`，线确实看得见了，但用户截图里四个框仍只有上边和左边。逐像素解码
   700×525 原图：`#5C85BC` 有 3010 个像素，却只出现在 y=143/213/321/412/425 五条水平线和
   x=42 一列上，四个框的下边、右边全是 `#16263F` 底色 —— 不是被抹掉，是根本没画出来。
   根因在几何：`WM_NCCALCSIZE` 让出的客户区是 `[bw, w-bw) × [pad, h-bw)`，细线样式
   `border: 6` 当时 `bw = 1`；`sk_edit_ring()` 按可见区 `[0, w-1) × [0, h-1)` 画 1px 环，
   右带落在 `x = w-2`、下带落在 `y = h-2`，**两处都在客户区里**，EDIT 一重绘客户区
   （输入 / 选中 / 光标闪烁）就把它们刷成底色；上 / 左带在 `x=0`、`y=0` 的非客户区，
   所以留下来。**修复**：`CG_EDIT_BORDER` 统一为 3（客户区四边各让 3px = 2px 环 +
   1px 给被圆角窗口区域裁掉的最外列 / 行留余量），`sk_edit_ring()` 改为「外圆角区域
   `[0,w-1)` − 内圆角区域 `[2,w-3)`」，右 / 下带 `x∈{w-3,w-2}`、`y∈{h-3,h-2}`
   全在非客户区内；`sk_edit_box()` 在 `WM_PAINT` 画完客户区后再补一次边框。
   实测真实屏幕截图三态（初始 / 输入文字触发重绘 / 失焦）四个框都是「上 2 行 + 下 2 行 +
   左右 2 列」的闭合边框，三态像素完全一致。另外一直开着的旧窗口不会因重新编译而刷新，
   要关掉重开。
3. **构建产物可能是旧的 —— 源码与界面资源都加了内容指纹**：`designer/electron/cgbuild.mjs`
   原来只比 mtime（`-MMD` 生成的 `.d`），源码被 git / 打包工具还原成旧时间戳时，`.o` 比
   `.c` 还新，增量判定就判"已是最新"，源码里的修复永远进不了 `.a` / exe —— 用户机器上
   看到旧渲染就是这个。现在每个 `.c` 编译成功后在 `build/obj/` 写一份 SHA-1 指纹 `.sig`；
   **内嵌界面资源同理**：`${name}_cgui_res.o` 只比 `.cgui` 的 mtime，界面改了却漏编进 exe
   也会让人以为"编译没生效"，现在把 `.rc` 与 `.cgui` 字节一起算进
   `${name}_cgui_res.sig`。实测把源码 mtime 倒填到 2020 年（比 `.o` 早 6 年）仍能抓到
   并重编，二次构建全部跳过。
4. **别用 `shape` 垫一层外框来「补线」**：给每个 `edit` 外扩 2px 放一个
   `format: roundrect` 的 `shape`，截图里四边细线确实完整好看，但 `shape` 是独立子窗口，
   会抢焦点 / 吃掉点击 —— 交互探针 9 项断言全挂（公式框永远停在初始值 `12 + 7 × 3`）。
   撤掉 `shape` 后立刻全部恢复。运行时修好之后更不需要这种绕法；视觉与交互冲突时优先保交互。
5. **别在运行时用 `cg_widget_set_colors` 改 `edit` 的字色**：`style.fg` 同时被自绘层拿去画描边，
   改字色会让结果框冒出一圈白边。配色统一交给 `.cgui`。
6. **多行框加 `scroll` 会带出浅色系统滚动条**：Windows 经典控件染不到深色，索性去掉滚动条，
   靠键盘 / 滚轮滚动，视觉干净得多。
7. **单行输入框的回车 / Esc 到此为止**：`IsDialogMessage` 把它们转成 `WM_COMMAND(IDOK/IDCANCEL)`，
   而这条命令的 `lParam` 为 0 时会被消息循环的"菜单命令"分支先截走，`submit` 不派发
   （控制台会打「收到未知的菜单命令 1」）。所以本示例**不承诺回车求值**，改靠 `change`
   实时预览 + 按钮 `click`；`.cgui` 里仍保留 `submit` 绑定作为事件表的示范，但不依赖它。
8. **UTF-8 符号别手数字节数**：`×` 是 2 字节、`−` 是 3 字节，写死长度会把 `×` 认成非法字符。
   归一化改成 `k_syms[]` 表驱动、长度一律 `strlen`。
9. **跨进程读控件文字要用 `WM_GETTEXT`**：验证探针里 `GetWindowText` 只拿到创建时的旧值
   （一直返回初始的 `33`），显式 `SendMessageW(h, WM_GETTEXT, ...)` 才读到实时结果。
10. **只读右对齐结果框会"多一条竖线 + 字贴边"**：结果框是 `input: 1`（→ `ES_READONLY`）
    加 `style.align: right`（→ `ES_RIGHT`）。点它聚焦时 Win32 照样画插入符、且停在文本开头，
    右对齐的 `33` 在另一端，那条米白竖线就孤零零压在数字左边；`ES_RIGHT` 又把文字贴到
    客户区右边界，叠上 2px 焦点环后最后一个字符看着像被右边框压住。修复在公共运行时
    `runtime/src/skin/cg_skin_edit.c`：只读框在 `WM_SETFOCUS` / `WM_PAINT` 之后 `HideCaret()`；
    右对齐框右边距从 6px 加到 16px，并把值存进子类 `s->right` —— 只在
    `cg_skin_apply_edit()` 设一次会被建控件后换字体、`WM_SIZE` 重排时重发的
    `EM_SETMARGINS` 冲掉（`EM_GETMARGINS` 实测只剩 `right=2`），所以三处重设左边距时
    都一起带回（有调节器的数值框仍用 2px 让位）。实测点击结果框后连拍三张（覆盖插入符
    闪烁周期）：竖线像素 0，文字到右边框间距 5px → 17px。
11. **"还是被遮挡"其实是文本被选中，不是被压住**：第三轮截图逐像素解码后，结果框里
    `33` 是 `#0078D7` 系统高亮蓝底 + 白字（516 / 140 个像素），外加紫色焦点环 1955 个像素；
    前两轮修的插入符和 17px 右边距都已生效（数字 x=477..499、右边框 x=517），但没管
    **选中态**。Win32 EDIT 只在有焦点时画系统高亮，双击数字 / 拖选 / `Ctrl+A` 就会留下
    这块深色主题里极突兀的"贴片"（Python ctypes 探针复现：双击 `33` 后 `EM_GETSEL`
    变成 `0..2` 全选）。修复仍在 `runtime/src/skin/cg_skin_edit.c`：给**只读单行**展示框
    置 `s->display` —— 去掉 `WS_TABSTOP`、吞掉 `WM_LBUTTONDOWN` / `WM_LBUTTONDBLCLK` /
    右键 / 键盘、`WM_SETFOCUS` 把焦点还给上一个窗口、`WM_SETCURSOR` 改用箭头光标；
    没有焦点就不会画高亮，也不再画焦点环与插入符。**多行只读输出区不受影响**（日志 /
    终端仍要能选中复制），判断条件是 `ES_READONLY && !ES_MULTILINE`。
    验证：初始 / 点击 / 双击 / `Ctrl+A` / 拖选五态真实屏幕截图，系统蓝 516→0、白字 140→0、
    紫色环 1955→0，青色 `33` 稳定在 x=479..499，四边闭合；真键盘真鼠标探针确认只读框
    仍能被程序更新（统计 `30/38/1` → `0/0/0` → 点按钮 `3/3/1`）。
    **取舍**：结果 / 统计框变成纯展示，不能再拖选复制；要复制得另加"复制结果"按钮。
12. **可编辑框选中时"整条输入框被蓝色盖住"**：第四轮截图里公式框输入一长串数字后
    `Ctrl+A` 全选，`#0078D7` 系统高亮铺满 x=51..649（9804 个像素）、一直顶到右边框，
    输入框本身几乎看不见。上一轮只把只读展示框改成"不参与焦点"，**可编辑框不能这么干**
    （还要能输入 / 拖选 / 复制），必须从选中态本身下手。
    **最大的坑**：标准 EDIT 的选中高亮**不走 `WM_PAINT`** —— 它是控件内部拿 `GetDC`
    直接画的。临时诊断日志显示 `Ctrl+A` 之后一条 `WM_PAINT` 都没有，所以第一版把染色
    挂在 `WM_PAINT` 上完全没生效（蓝底依旧 8700 像素）。现在
    `sk_edit_retint_selection()` 在 `WM_PAINT` **以及** `WM_KEYDOWN` / `WM_CHAR` /
    `WM_SYSCHAR` / `WM_LBUTTONDOWN` / `WM_LBUTTONUP` / `WM_LBUTTONDBLCLK` /
    `WM_MOUSEMOVE` / `EM_SETSEL` / `WM_SETFOCUS` 之后都跑一次：先把客户区读进 32bpp
    DIB，凡是落在「`COLOR_HIGHLIGHT` → `COLOR_HIGHLIGHTTEXT`」这条抗锯齿色带上的像素，
    按同一个混合系数重映射到「输入框底色（+16）→ 近白文字」；投影 + 距离阈值保证普通
    底色 / 普通文字不被误改，处理幂等；浅色底（亮度 > 128）保持系统默认选中色。
    实测 `Ctrl+A` 全选 / 鼠标拖选 / 多行框全选三种路径亮蓝底 **9804 → 0**，换成一层
    几乎融进输入框的淡底色（8700 / 5244 / 3050 像素），四边边框完整，取消选中后完全
    恢复；真键盘真鼠标功能探针 4/4 通过（拦截键盘消息没有影响输入与 `change` 派发）。
    **取舍**：选中反馈现在是"极淡底色 + 白字"，不再是系统亮蓝；想连这层淡底都不要，
    把 `sk_edit_retint_selection()` 里 `nr/ng/nb += 16` 三行删掉即可（选中只靠文字提亮）。
13. **聚焦框"右边框只有一条孤立竖线、上下圆角断开"**：第五轮截图逐像素比对同一张图里
    的两个框，才把范围缩到「只有聚焦的那个坏」——未聚焦的多行框右端 x=654..655 两列
    从圆弧到竖线全程连续，聚焦的公式框圆弧到 y=149 就停，y=150/151 两行空白，竖线只剩
    x=655 一列，y=168..170 又断三行。根因是第 12 条那个染色函数的**整块客户区
    `BitBlt(dc, 0, 0, w, h, ...)`**：圆角半径（`radius: 10`）大于边框带宽（`bw=3`），
    圆弧有 7px 落在客户区里；聚焦时每次键盘 / 鼠标消息都把整个客户区写回一遍，就把
    圆弧在客户区里的那截抹成底色，而染色只在有焦点时才跑 —— 所以非聚焦框完好。
    修复两处，都在 `runtime/src/skin/cg_skin_edit.c`：① 染色只 `BitBlt` **改动像素的
    包围盒**，零改动时连写回都不做；② 在所有会重绘客户区的消息（键盘 / 鼠标 /
    `EM_SETSEL` / 焦点变化 / `WM_PAINT`）处理完之后**无条件补画一次 `sk_edit_box()`**，
    不能只在"染色改了像素"时补 —— 点击取消选中后选区为空、染色提前返回，但 EDIT
    内部已经重绘过客户区，仍需要补画（第一次改完实测只有 `6-deselected` 还断，就是
    漏了这条）。标准 EDIT 这类内部重绘是 `GetDC` 直接画的，**不发 `WM_PAINT`**，
    光靠 `WM_PAINT` 里补边框不够。
    验证 `tmp/diag_selection_retint.ps1` 九态真实屏幕截图（含选中后高频鼠标移动）：
    九个状态公式框左 2 列 / 右 2 列、圆弧→竖线**零断口**，染色仍生效（系统蓝 0、
    淡选中底 8700 / 8721 / 5244）；真键盘真鼠标功能探针 7/7（含全选与取消选中）。
    **后续修正**：上面这套「消息后无条件补画」只适用于**单行框**。pre-push 门禁的
    C 单测抓到回归：多行 EDIT 流式灌日志时，`EM_SETSEL` / `WM_PAINT` 里刚画好的灰环
    会被 `ScrollDC` 一起滚进客户区中间，变成一条横贯的实心线（开始滚动那一轮才出现）。
    多行框因此回到提交前的「焦点 / `WM_NCPAINT` 补画」，选中染色仍照常生效。

## 六、边界照实说

- **深色标题栏做不到**：`app.dark: true` 只改客户区与控件配色，窗口标题栏是系统画的浅色。
- **不承诺键盘快捷键**：回车 / Esc 会被上面的消息循环吃掉；本示例的核心交互是"打字即出结果"。
- **`%` 是"数字 ÷ 100"**，不是"相对上一个操作数的百分之几"。
- **换行计入字符数与字节数**：`中文\nabc` → 6 字符 / 10 字节 / 2 行。
- **工程目录名必须 ASCII**：MinGW 工具链限制，不是框架限制。
- 仓库里另有 `examples\calculator\`（另一路会话建的同类示例），两者互不影响。
